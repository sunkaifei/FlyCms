## 一、复核方法

清单存在的意义是「只有跑过验收标准才允许打 `[x]`」。所以本次复核**刻意不复用清单的自述**，而是分三层独立取证：

| 层 | 做法 | 能发现什么 |
|---|---|---|
| **静态核查** | 逐文件确认「改动文件」存在、内容与声明一致；对量化声明（如「清零」「55/55」）写脚本重新计数 | 虚标、措辞夸大 |
| **动态实测** | 对每个能力直接发 HTTP 请求 / 查库 / 看磁盘，验证「行为」而非「接口存在」 | 接口在但功能坏 |
| **盲区补测** | 找出 e2e 未覆盖的维度（未被测的 pageType、未被测的操作分支、未被测的调用形态） | 覆盖假象 |

关键差异在于：**「接口存在」不等于「功能可用」，「编译/类型检查通过」不等于「运行时正确」**。本次 6 个缺陷中有 4 个正是卡在这个缝隙里。

## 三、新发现的真实缺陷

### D1【阻断级】导出的主题包无法导入回系统（格式不对称）

| 项 | 内容 |
|---|---|
| **现象** | 用「导出」下载的 zip 原样「导入」，必然失败 |
| **实测** | 导出包首条目 = `manifest.json`（根级文件，无 `/`）→ 导入器取「首个文件路径第一段」当皮肤名 → `indexOf('/') == -1` → `skin = null` → 返回 `{"code":-1,"message":"皮肤包首层目录名非法：null"}` |
| **根因** | `TemplateCenterService.importSkin()` 第 531-534 行：<br>`if (skin == null) { int i = rel.indexOf('/'); skin = i > 0 ? rel.substring(0, i) : null; }`<br>它假设「zip 内每个条目都在 `<皮肤名>/` 之下」，于是取第一段；而 `exportSkin()` 产出的包**第一个条目是根级 `manifest.json`**，直接判空。两套格式互不认识 |
| **影响** | 主题包的分发/备份/迁移能力**实际为零**——用户点「导出」拿到的包，拿到别处点「导入」只会得到一句「首层目录名非法」。这是 P2-1 的核心价值，却是唯一没被验到的分支 |
| **复现** | `python tools/audit_extra_check.py` 第 ③ 组 |

### D2【高】带 `pc_theme/` 前缀的包会把父目录名当皮肤名

| 项 | 内容 |
|---|---|
| **现象** | 导入 `pc_theme/auditskin/{theme.json,index.html}` → 提示 `皮肤「pc_theme」已导入，写入 2 个文件`，期望的 `auditskin` **根本没被创建** |
| **实测** | 导入后磁盘出现 `views/templates/pc_theme/pc_theme/auditskin/...`（同名嵌套）；`theme/list` 多出 `code=pc_theme` 一项；随后 `deleteSkin("auditskin")` → `皮肤不存在：auditskin` |
| **根因** | 同 D1 的「取第一段」逻辑 + `SKIN_NAME` 正则允许 `pc_theme`（与主题根目录同名），无保留名校验 |
| **影响** | 主题根目录被污染并自我嵌套；皮肤名与主题根同名会让「主题目录 = 皮肤目录 = 主题目录」产生歧义 |

### D3【高】标签手册 7 个骨架复制后直接报错

清单称「手册表按真实注册名全量重写（**55/55 零偏差**）」。注册名确实全对，但把 55 个骨架逐个送进官方「试渲染」接口后：**OK 37 / 失败 18**，其中 **7 个是与运行上下文无关的硬缺陷**（复制即错）：

| 标签 | 手册骨架写法 | 真实情况 | 缺陷类型 |
|---|---|---|---|
| `fly_linkspage` | `${l.url}` / `${l.name}` | `Links` 实体字段是 `linkUrl` / `linkName` | 字段名错 |
| `fly_areaslist` | `${a.id}` / `${a.name}` | `Areas` 实体字段是 `areaId` / `areaName` | 字段名错 |
| `fly_topicpage` | `${t.topicName}` | `Topic` 实体字段是 `topic` | 字段名错 |
| `fly_avatar` | `<@fly_avatar avatar="..."/>` | 标签读 `params.get("avatarurl")` 与 `params.get("avatar")`，**两者都无空值防御** → 缺 `avatarurl` 时 `.toString()` 抛 NPE | 骨架缺参 + 标签不健壮（**双重**） |
| `fly_useractivation` | `<#if (status!0) == 1>` | `status` 由标签置为 **boolean** → boolean 与数字比较抛 `Can't compare values of these types` | 骨架写法错 |
| `fly_checktagfollow` | `<#if (result!0) == 1>` | 同上（`result` 是 boolean） | 骨架写法错 |
| `fly_order` | `<#if order??>${order.orderNo!''}</#if>` | `order` 非 hash，`??` 为真后取属性抛 `Expected a hash` | 骨架写法错 |

> 另有 **11 个**失败是因为骨架引用了页面上下文变量（`article`/`channel`/`question`/`answer`/`share`/`userinfo`/`form`/`categoryList`/`fieldsList`/`type`），而 `sampleModel()` 只 mock 了 `info` 与 `dataList`。这类在前台运行时是正常的，但用户点「试渲染」会看到一堆报错——属**体验缺陷**，不是手册错。

### D4【中】`/system/template/preview` 的错误检测不一致（靠「是否抛异常」判定）

| 项 | 内容 |
|---|---|
| **现象** | 同样是渲染报错，有的返回 `code=-1`，有的返回 `code=0「操作成功」`且报错块内联在 `html` 里 |
| **实测** | ① 错误写在模板**顶层** → 渲染抛异常 → `code=-1`；② 错误写在**标签体内** → 被标签自身的降级 `catch` 吞掉 → `code=0`，但 `html` 里含 `FreeMarker template error` |
| **根因** | `preview()` 第 814-824 行只 `catch (Exception e)`。而 FreeMarker 默认 `template_exception_handler=DEBUG` **把报错写进输出流而不抛**，且标签的降级逻辑会在标签体渲染时吞掉异常——两条路径都逃过检测 |
| **影响** | 与 P0-3 探活踩的坑**同源**：`ThemeHealthChecker` 已经知道要 grep 响应体里的 `FreeMarker template error`，而 `preview` 没有做同样的事。「试渲染说成功、实际是报错」会误导使用者 |

### D5【中】「静默吞异常清零」不成立（P3-5 的量化结论失效）

| 项 | 内容 |
|---|---|
| **`printStackTrace()`** | 残留 **16 个文件 / 约 31 处**。其中业务类 3 个：`web/front/UserController.java`、`module/article/service/ArticleCategoryService.java`、`module/question/service/ImagesService.java`；其余在 `core/utils/*` 工具类（`LucbirSearcher` 单文件 7 处） |
| **`catch (Exception ignored)`** | 残留 **6 处**：`ThemeRegistry.java:204`（有 `logger.debug`）、`AdminLogInterceptor.java:129`（仅注释）、`TemplateCenterService.java:211`（有 `logger.debug`）/ `:867`（**无日志**）/ `:879`（**无日志**）、`TagSuggestService.java:233`（**无日志**） |
| **判定** | 31 个标签类的「降级留痕」改造**确证有效**；但清单验收标准里的「全仓清零」是**过度声明**。准确表述应为：「标签层全量留痕；非标签位置减少但未清零，仍有 6 处静默 catch，其中 3 处无日志」 |
| **附带发现** | 清单 P3-5 标题点名的 `ThemeRegistry.markCurrent()` —— 该方法实际位于 `ThemeSwitchService`（第 189 行），且**已改造为 `logger.warn`**。清单的行号/类名描述不准，但问题确实修了 |

### D6【中】`deleteSkin` 不清理 `fly_theme` 登记

| 项 | 内容 |
|---|---|
| **现象** | 删除主题后，磁盘目录消失、`fly_template` / `fly_template_version` 已清，但 `fly_theme` 里那一行**仍在** |
| **实测** | 本轮核查删除 `defalut_child_audit` 与 `pc_theme` 后，`select code from fly_theme` 仍返回这两行；需手工 `delete` 才干净 |
| **根因** | `deleteSkin()`（第 155 行起）调 `templateDao.deleteVersions/deleteTemplatesBySkin` 与删目录，**没有 `themeDao` 调用** |
| **影响** | 与 §17.3 第 7 项（`is_current` 强一致）不同的问题面：孤行会长期积累，直到下次**重启**由 `ThemeBootstrap` 的反向清理兜底。这使「启动自愈」变成了唯一清理路径，而它只在启动时跑 |
