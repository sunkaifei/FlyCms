## 二、高危问题详情

### S1 评论内容存储型 XSS

**证据链**

1. `CommentService.addComment`（`module/comment/service/CommentService.java:126`）只做违禁词替换：
```java
text = filterKeywordService.doFilter(text);
```
2. `FilterKeywordService.doFilter` 仅把敏感词替换成 `*`，**不剥离 HTML 标签**，`<img src=x onerror=alert(document.cookie)>` 原样入库。
3. `Commentpage`（`web/tags/Commentpage.java:90,99`）把 `content` / `nickname` 原样放进行 Map，其类注释给出的模板用法是 `${c.content}` / `${c.nickname}`。
4. FreeMarker `${}` **不做 HTML 转义**，且项目未配置 `output_format=HTMLOutputFormat`（`application.yml` 的 `freemarker.settings` 只有 `auto_import` / `number_format`）。

**影响**：一旦主题按官方文档渲染评论（`pc_theme` 目前尚未接该标签，属**潜伏型**），任意登录用户可通过评论在**所有访客浏览器**执行脚本 —— 窃取会话（`FlyCmsId` 若未设 HttpOnly）、篡改页面、挂马。`nickname` 同样可控（用户中心可改昵称），且后台审核时不易察觉。

**修复**：写入侧统一清洗，与表单通道保持一致（`FormService` 已用 jsoup）。
```java
// CommentService.addComment，违禁词过滤之后
text = JsoupUtils.clean(text);
```
同时建议给昵称输出加 `?html`，并在 `Commentpage` 的官方示例中改为 `${c.content?html}`。

### S2 SSRF + 本地文件读取（图片本地化）

**位置**：`module/images/service/ImagesService.java:309-346`（`replaceContent`）、`:654-673`（`saveUrlAs`）

```java
Pattern pRemoteFileurl = Pattern.compile("<img.*?src=\"?(.*?)(\"|>|\\s+)");
...
String reg = "(?!.*((img.baidu.com)|(127.0.0.1)|(^/upload/content/))).*$";
if (remoteFileurl.matches(reg)) {
    saveUrlAs(remoteFileurl, Const.UPLOAD_PATH + imgpath + filename);   // ← 直接落盘
}
```
```java
public static boolean saveUrlAs(String fileUrl, String savePath) {
    URL url = new URL(fileUrl);                       // ← 协议不限
    HttpURLConnection connection = (HttpURLConnection) url.openConnection();  // ← 无超时
    ...
}
```

**问题**
1. **协议不限**：`file:///c:/windows/win.ini` 可被读取并写入 `uploadfiles/content/yyyy/MM/dd/*`，而该目录在 `spring.web.resources.static-locations` 中**对外公开**（`application.yml:14`）→ 本地任意文件读取 + 外泄。
2. **主机不限**：内网 `http://192.168.x.x/`、云元数据 `http://169.254.169.254/latest/meta-data/`、`http://127.0.0.1:6379` 等均可达；排除正则只写了 `127.0.0.1` 与 `img.baidu.com`，且 `127.0.0.1`（localhost）本身也被当作「允许」而放行到下一分支。
3. **无 connectTimeout / readTimeout**：恶意或极慢的 URL 会长期占用 Tomcat 工作线程；与 `druid.maxActive=20` 叠加可造成**线程 + 连接池双重耗尽**（见 P1）。
4. **无响应体大小与 Content-Type 校验**：抓回的内容按 URL 后缀决定落盘扩展名，`getImageUrlSuffix` 对 `.svg` / `.html` 不设防 → 落盘为可执行脚本 → 组合成存储型 XSS。

**修复**
```java
private static final Set<String> ALLOW_PROTOCOL = Set.of("http", "https");
// 1) 协议白名单；2) 解析域名 → 拒绝私有/回环/链路本地/元数据地址（含 169.254.0.0/16、10/8、172.16/12、192.168/16）
// 3) setConnectTimeout(3000) / setReadTimeout(5000)
// 4) 限制 Content-Length 与累计读取字节（如 5MB）
// 5) 白名单扩展名（jpg/png/gif/webp/bmp），并复用 UploadSafeUtil.ImageType.magicMatches 校验魔数
```
建议直接复用 `UploadSafeUtil`：下载到临时文件后走 `safeImage` 校验，通过再落盘。

### S3 违禁词引擎线程不安全

**位置**：`module/other/service/FilterKeywordService.java:41-42, 187-220`

```java
private static final FilterSet set = new FilterSet();          // 静态共享
private static final Map<Integer, WordNode> nodes = new HashMap<>(1024, 1);  // 静态共享、非并发容器

public final String doFilter(final String src) {
    addSensitiveWord(this.getFilterKeywordAllList());   // ← 每次请求都往共享 HashMap 里写
    ...
}
```

**问题**：`nodes` 是普通 `HashMap`，`addSensitiveWord` 在**每次** `doFilter` 调用时都执行 `nodes.put(...)` / `fnode.addIfNoExist(...)`。两个并发请求同时触发扩容或改链表指针 → JDK7 时代的经典「HashMap 成环 → CPU 100%」，或 `WordNode` 链被破坏导致过滤错乱/死循环。`set`（`FilterSet`）同理。

**修复**：DFA 构建改为「词表版本号变更时才重建 + 双检锁/一次性构建」，构建完成后发布**不可变**结构（`Map.copyOf` 或 `ConcurrentHashMap` 并只在初始化阶段写）。
```java
private volatile Map<Integer, WordNode> nodes = Map.of();
private volatile int builtVersion = -1;
private synchronized void ensureBuilt() { /* 版本比对 + 一次性重建 */ }
```
另外 `getFilterKeywordAllList()` 已 `@Cacheable`，`doFilter` 里应移除「每次重建」这一步。

### S4 Druid 监控台暴露

**位置**：`config/DruidMonitorConfigurer.java:32-46`

```java
bean.addInitParameter("allow", "127.0.0.1");
bean.addInitParameter("loginUsername", "admin");
bean.addInitParameter("loginPassword", "flyCms2018");   // ← 源码硬编码
```

**问题**
1. **口令硬编码在源码**，且与历史项目（28844.com）同源，公开仓库 `sunkaifei/FlyCms` 可直接读到。
2. **白名单可被绕过**：Druid 的 `allow` 判定默认取 `request.getRemoteAddr()`。生产部署若为 `nginx(本机) → Spring Boot:80`，`remoteAddr` 恒为 `127.0.0.1`，白名单形同虚设，互联网可直达 `/druid/` 并查看 SQL、URI、会话信息（Druid 监控台历史上多次因未授权访问被利用）。

**修复**
1. 口令改环境变量（`FLYCMS_DRUID_PWD`），并在生产**直接不注册**该 Servlet（用 `@Profile("dev")`）。
2. 若必须保留：白名单改为真实出口网段，或在 nginx 层对 `/druid/` 再加一道鉴权。

## 三、中危问题详情

### S5 数据库口令默认值
`application.yml:45`：`password: ${FLYCMS_DB_PASSWORD:123456}`。默认弱口令，未注入环境变量即生效。建议改为必填占位（`${FLYCMS_DB_PASSWORD}`）让缺配置时启动失败。

### S6 CSRF 生产仍为监听模式
`application.yml:181`（prod profile）`flycms.security.csrf.enabled: false` —— 只记录不拦截。当前靠 `SameSite=Lax`（`:33`）兜底，对跨站 POST 有效；但一旦按 `:109` 注释把 `cookieDomain` 设为 `.example.com`，同站子域可发起 CSRF。建议 prod 切 `true`。

### S7 `?invite=` 未校验写入 Cookie
`filter/FlyFilter.java:72-75` + `core/utils/CookieUtils.java:36`：
```java
String invite = request.getParameter("invite");
if (!StringUtils.isBlank(invite)) {
    CookieUtils.writeCookie(httpResponse, "invite", invite, 60 * 60 * 24 * 7);
}
```
用户完全可控的字符串直接进 `Set-Cookie`。容器（Tomcat）校验较严时会抛 `IllegalArgumentException` → 500；宽松实现下可注入附加 Cookie（如覆盖会话键 `FlyCmsId` 造成会话固定）。**修复**：`invite` 仅允许数字 ID（`NumberUtils.isCreatable` 或正则 `^\d{1,19}$`），非法直接忽略。

### S8 皮肤包导入的 zip bomb
`TemplateCenterService.importSkin:528-557`：只校验**压缩包**大小 ≤ `MAX_PACK_BYTES`(50MB)，但把每个 entry 通过 `readAll(zis)` **全量读成 String 存内存**（`rawEntries`）。50MB 高压缩比 zip 可解压出数十 GB → 堆内存耗尽、进程 OOM。**修复**：累计解压字节上限（如 200MB）+ 单条目上限（如 5MB），超限即中止；另外把 entry 内容按期写入临时文件而非全部驻留内存。

### S9 排序白名单粒度不足
`core/utils/OrderbyUtils.java:18`：
```java
private static final Pattern SAFE_PATTERN = Pattern.compile("[A-Za-z0-9_.\\s,]+");
```
允许字母/数字/下划线/点/空白/逗号 —— 因此**无法**注入引号、括号、分号、注释符号，**经典注入已被阻断**（这一点做得对）。但它是字符白名单而非**列白名单**，仍允许：
- `ORDER BY <任意列>`（含未在前端暴露的敏感列，如用户口令散列字段）→ 通过观察返回顺序构成**排序侧信道 oracle**；
- 多字段 + 表别名（`a.id`）—— 表别名可跨表引用（若 SQL 存在 JOIN）。

**修复**：改为「列名枚举白名单 + 方向枚举」：
```java
if (!ALLOWED_COLUMNS.contains(col) || !("asc".equals(dir) || "desc".equals(dir))) return fallback;
```
（自定义模型的 `ModelDataService` 已按此思路实现，见 `SqlSafeUtil.safeOrderColumn`，可直接复用。）

## 四、性能问题详情

### P1 连接池偏小 + S2 可致耗尽
`application.yml:53` `maxActive: 20`，`maxWait: 60000`。S2 的无超时外网抓取会长期持有 Tomcat 线程与连接，20 个连接被打满后全站排队 60s 再失败。**修复**：先修 S2 的超时；再按压测量调大 `maxActive` 并加 `removeAbandoned`（Druid 参数）。

### P2 每请求 DB 往返（FlyFilter）
`FlyFilter.doFilter` 对**每个带会话 Cookie 的请求**执行 `findUserSessionBySeeeionKey` / `findUserById`（1~2 次查询），登录态无任何缓存；此外每请求调用一次 `redirectService.match`。全站流量下这是最容易被忽略的固定开销。**修复**：会话态加短 TTL 缓存（Caffeine/Guava，key = sessionKey，TTL 30~60s），或用已注入的 `HttpSession` 复用（当前逻辑在 session 命中时仍会再查一次 DB，可提前 return）。

### P3 自定义字段查询无法走索引
`ModelDataDao.xml:10-33` 建表仅有三条索引：`idx_category(category_id,status)`、`idx_short_url(short_url)`、`idx_user(user_id,status)`。而 `ModelDataService` 生成的 WHERE 中：
- 自定义字段等值筛选：`col = #{params.col}` —— 可 sargable，但**无索引** → 全表扫描；
- 日期范围筛选（`ModelDataService.java:221-224`）：`CAST(JSON_UNQUOTE(JSON_EXTRACT(col,'$[0]'))) >= ?` —— **函数包裹列，非 sargable**，必然全表扫描；
- 排序：`` ORDER BY `col` `` 无索引 → filesort。

数据量到万级后列表页会明显变慢。**修复**：给 `is_filter=1` 的字段在建模时同步建索引；日期范围若为高频筛选，考虑改用生成列（`GENERATED ALWAYS AS`）+ 索引，或拆成 `start_at` / `end_at` 两个真实列。

### P4 N+1 查询（评论）
- `Commentpage.java:94` 在 `for (Comment c : list)` 内逐条 `userService.findUserById(...)`。10 条评论 = 10 次查询。
- `CommentService.java:201` 在后台列表循环内逐行 `resolveTargetTitle(...)`。

**修复**：批量取用户（`findUsersByIds`）与批量取标题后在内存拼装。

### P5 聚合栏目 N 次查询 + 内存归并
`ChannelRenderService.aggregateRows:124-141` 对每个栏目各调一次 `selectPage(..., 100)`，再在内存 `merged.sort` 后分页。子栏目多时查询数线性增长，且计数来自内存列表（`merged.size()`）。代码注释已说明「千级以内场景」，属已知取舍，但建议在聚合栏目数量 > 阈值时改走缓存或异步。

### P6 前台标签分页无上限
`AbstractModelTag.intVal(p, "rows", 10)` 无上限；`PageVo.getRows()` 无 clamp。API 侧已限制（`ApiModelController:438` 上限 200、`TagService.MAX_ROWS=100`、`UserService:1044` 上限 200），但 FreeMarker 标签路径没有。当前全仓模板未出现 `rows="${...}"`（已 grep 确认），风险取决于主题作者；建议在 `intVal` 层统一 clamp（如 1~100）。

### P7 微缓存 key 用 `hashCode()`
`AbstractModelTag.tagCache:172` 用 `tagName + modelCode + params.hashCode()` 作 key。`Map.hashCode()` 碰撞概率虽低，但碰撞会导致**跨参数串数据**（返回错误的缓存结果）。建议改用 `params.toString()` 或拼接排序后的键值对。

### P8 Druid 统计过滤器挂错路径
`DruidMonitorConfigurer.java:56` `bean.addUrlPatterns("/admin/*")` —— 与 `StatViewServlet` 的 `/druid/*` 不匹配，`filters: stat,wall` 的 SQL 统计基本收不到数据。应改为 `/*`。

## 五、做得好的地方（建议保持）

1. **动态 SQL 安全边界清晰**：`SqlSafeUtil` 对「字段名 / 表名后缀 / 数字」分别用**独立命名**的白名单+双黑名单校验；`ModelDataService` 的 `whereSql` / `orderBySql` **全部由服务端依元数据生成**，值一律走 `#{params.*}` 预编译，`SELECT` 列投影也走白名单（G11）。注释还写明了「安全边界不同的校验必须独立命名」——这一点做得非常专业。
2. **上传三重校验**：`UploadSafeUtil` 强制「扩展名 + MIME + 文件头魔数」三者一致，并强制 UUID 重命名；白名单**不含 SVG/HTML**，有效阻断「上传即 XSS」。
3. **Zip Slip 有防护**：`TemplateCenterService.importSkin:615-621` 与 `WpThemeConverterService.unzip:705-710` 都在落盘前做 `normalize().toAbsolutePath()` + `startsWith(root)` 校验，越界即整体拒绝。
4. **无命令执行 / 无 Java 反序列化**：全仓 grep `Runtime.exec` / `ProcessBuilder` / `ObjectInputStream` / `readObject()` 均为 0 命中。
5. **前端无 DOM 型 XSS 入口**：`frontend/apps` 全量无 `v-html` / `innerHTML` / `dangerouslySetInnerHTML`；Vue 默认转义。
6. **表单公开通道防护完整**：`ApiFormSubmitController` + `FormService` 具备「验证码（一次性）→ IP/用户每日频控 → 必填校验 → jsoup 清洗 → 敏感词过滤」，且注释明确说明为何不继承 `ApiBaseController`。
7. **权限粒度完整**：`ApiBaseController` 统一 401/403，模型数据按 `list/add/edit/del@{modelId}` 四粒度锚点鉴权，另有 G14 字段级权限（读剔除 + 写拒绝）。
8. **序列化契约正确**：Long → String 规避 JS `MAX_SAFE_INTEGER` 精度丢失；SQL 参数化 + `OrderbyUtils` 阻断经典 ORDER BY 注入。
