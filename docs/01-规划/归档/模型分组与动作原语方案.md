## 0. 结论（回应"商城能不能纯自定义模型做出来"）

| 层 | 谁做 | 商城上线后还要写代码吗 |
|---|---|---|
| ① **模型分组**（组织层） | 一次性引擎开发 | ❌ 永不——以后任何模块（楼盘/课程/问答）纯后台建组 |
| ② **动作原语**（动作层） | 一次性引擎开发 | ❌ 永不——点赞/报名/积分全是同一批端点的用户 |
| ③ **商城组装**（业务层） | **纯后台**：建分组→建模型→绑字段→做模板 | ❌ 改价/上下架/加分类/调模板全后台 |

判定标准：**商城的"业务"一行代码不写；"引擎的通用机制"写一次，所有业务共用**——
与"动态 DDL 也是写出来的，但建任何内容模型从此纯后台"同一逻辑。

### 用户的原始诉求与两段式回应

> "一个商城模块里可以用到多个表，怎么互相管理全部通过模型设置、字段绑定等办法创建，
> 但应该是多个表，不可能每个表都叫一个模型，按道理是模型下建立相关表。"

- **"模型下建多张表"的合理内核 = 组织层**：分组（fly_model_group）把多模型聚合成一个业务
  模块入口（菜单子目录+管理页聚合），管理员看到的是"商城"一个模块、下面挂着商品/SKU/
  购物车/订单四张表；
- **"每张表"的存储语义保持一模型一表**（生命周期/权限/模板语义完全不同的表不强行捆一个
  删除键），表间"互相管理" = relate 字段绑定（skus.product→products）+ 分组内推荐；
- **运行时动作**（加购/下单/扣库存）由 ② 动作原语补齐——这是"模型设置+字段绑定"管不了
  的第四层（查询/展示/投稿之外的动作层），通用端点零业务代码。

## 1. ① 模型分组（组织层，已落地）

**表**：`fly_model_group(id, name, code 唯一, icon, description, sort, status)` + `fly_model.group_id`（NULL=未分组）。

**端点**（/api/system/modelGroup/*，权限复用模型管理）：
`GET list?status=`（装填组内模型）/ `POST save`（id 空=新增，code 创建后不可改）/ `POST del`（组内模型须先移出）。

**模型归组**：`POST /api/system/model/update` 带 `groupId`（未传=不变更，传空=移出）。

**菜单聚合**：后台「模型管理」页按分组聚合展示（未分组模型保持平铺）；停用分组仅隐藏聚合入口不动模型。

## 2. ② 动作原语（动作层，已落地）

三个通用端点（`/ucenter/action/**`，登录态，权限行 `/ucenter/action/*` 已授权全部用户组）：

| 原语 | 端点 | 语义 |
|---|---|---|
| **动作流写入** | `POST /ucenter/action/{modelCode}`（body 表单；`rows` JSON 数组=批量） | 登录用户向任意启用模型提交行；复用 insertData 全链路校验/引用计数/版本快照/事件；**title 缺省自动派生**（动作模型无标题语义）；status 不走审核开关（默认 1） |
| **字段原子增减** | `GET/POST /ucenter/action/{modelCode}/{id}/counter?field=&delta=` | `field = field + delta`（DB 端并发安全）；仅 number/decimal；负增量受字段 min_value 下限守卫（不足即整拒，防超卖） |
| **组合事务** | `POST /ucenter/action/compose`（actions=JSON） | 逐条执行 insert/counter；失败即**逆向补偿全部已执行**（insert 硬删回滚、counter 反向 delta），补偿失败留 ERROR 日志人工核对 |

**调用示例（下单）**：
```
POST /ucenter/action/orders            → 订单主行（普通 submit）
POST /ucenter/action/compose           → actions=[
  {op:"insert", model:"order_items", fields:{order_id:.., sku_id:.., qty:2, ...}},
  {op:"counter", model:"skus", id:SKU_ID, field:"stock", delta:-2}]
  → 明细落行 + 库存扣 2；第二步失败则第一步已插入的明细自动删除
```

**安全边界**：counter 列名过 safeColumnName 白名单；compose 的字段值全部经既有字段校验
（convertFieldValue）；未登录被 UserInterceptor 拦截；模型间引用存在性（sku_id 是否真 SKU）
属业务层职责（模板/前台脚本预检），原语保持通用不做模型推断。

## 3. ③ 商城组装（纯后台，已按通道执行 = 管理员可复刻的操作清单）

1. **建分组**：模型管理 → 新建分组「商城」（code=mall）；
2. **建 5 模型**（归组）：products 商品 / skus SKU / carts 购物车行 / orders 订单 / order_items 订单明细；
3. **字段绑定**（表间关系的全部秘密）：
   - products：brand_id(relate→brands) / gallery(images) / summary(textarea)；
   - skus：product(relate→products，**is_filter=1**——详情页按商品筛 SKU) / spec / price(decimal，**min_value=0**) / stock(number，**min_value=0**——防超卖下限)；
   - carts：sku_id / qty；orders：amount/consignee/phone/address/remark；
   - order_items：order_id/sku_id/product_id/spec/price/qty（price 为**价格快照**——改价不影响已成交）；
4. **商品分类**：products 分类树（数码/家居/服饰）；
5. **四页模板**：list-products（分类条+商品卡网格）/ detail-products（区间价+SKU 选择+加购表单）/ mall-cart / mall-orders（确认收货=X2 所有者通道）；
6. 前台即得：`/products/` 列表、`/products/{shortUrl}.html` 详情（登录可见加购，匿名见"登录后购买"）。

## 4. 验收（probe_mall 21/21 + 浏览器路径）

- 分组聚合（5 模型）；原语 submit 加购/重复加购独立行；counter 扣库存与读回、超下限拒绝；
- compose 明细+扣库存、失败回滚（废明细被删、库存未动）；
- 安全：伪造 sku_id 不 500（业务层校验）、未登录拦截；
- 展示域：/products/ 列表、详情区间价（¥49.90~¥89.00）、规格选择、登录视角加购表单、真实加购成功。

## 5. 不做清单（边界与后置）

- **在线支付/退款/优惠/运费**：外部依赖（网关/资质），预留字段与状态位，接入时纯后台+一次性回调对接；
- **多商家分账**：X 批次 enable_submit 已可让商家发商品；分账交易另立项；
- **订单状态机硬约束**：动作层模型的 status 由模板按钮/X2 通道更新（语义由界面按钮决定）；硬状态机校验可作后续原语 5（`op:"update"`）；
- ** carts 合并数量**：原语保持通用（重复加购=独立行），合并属业务语义由前台脚本 find+qty 更新实现；
- **遗留 module/order**：与硬编码商城方案一同否决，本批未触碰（退役候补）。
