## 2. 架构判断：为什么不需要"多表模型"

2.1 **"模型"在本引擎里是存储单元，"频道"是编排单元**。问答 = questions（问题）+ answers（回答）两个存储单元 + 一条 relate 边。这与 Dede 的"问答模块"（question/answer 两张硬表）在数据结构上同构——区别只在 Dede 把两表关系写死在代码里，FlyCms 用 relate 字段后台可配。强行发明"一个业务模型绑多表"的新对象，等于把 relate 机制再封装一遍，还要解决"级联删除/表单聚合/权限聚合"一堆派生复杂度——**E1 + 双向标注 + 字段筛选已经覆盖这三件事**（级联=deleteModel 级联+删除联动清引用；表单=投稿/编辑按模型分开；权限=模型粒度+字段粒度 G14 均已存在）。

2.2 **什么时候才真的需要多表**：同一行内容内部的一对多结构（如商品的多个 SKU）——这已经由 GROUP/REPEATER（P1 结构层，JSON 子字段）覆盖；跨模型聚合——由双向标注/relates/M2A 覆盖。其余"多表配合"都是**两个模型 + relate 边**能表达的。

2.3 **判定规则（写给后续所有频道需求）**：新频道需求进来先问三个问题——① 有几种"行形态"？（问答=2：问题行、回答行 → 两个模型）② 行间什么关系？（回答归属问题 → relate 字段 + is_filter）③ 谁在前台对哪类行做什么？（提问/回答/采纳 → enable_submit + X1 + X2）。三问答完，频道组装方案自动成立，全程后台+模板，零 Java 代码。

## 3. X1 投稿上下文预置（定向回答）

**能力定义**：投稿入口可携带 URL 参数预置表单字段值——仅限 id 类字段（relate / user / category / 固有 category_id），值必须通过既有存在性校验；GET 表单只读展示；POST 服务端**强制覆写**（URL 篡改无效，服务端为唯一事实源）。

**设计**：
- GET `/ucenter/submit/{code}?question=123`：白名单 = is_form=1 的 relate/user/category 字段名 + `categoryId`；值过 `checkReferences`/`findCategoryById` 等存在性校验，通过后放入 `meta.fixed`（Map：字段名→{value, label}——label 从目标行 title 解析，模板渲染"回答问题：xxx"只读条）；校验失败 404 语义。
- POST `/ucenter/submit/{code}`：同样的白名单解析 `fixed_*` 前缀参数（或同名参数），**服务端强制覆写** filtered 里的对应键（防越权改关联）；存在性校验同 GET。
- 表单模板（submit.html）加一段通用约定：`<#if meta.fixed??>` 渲染只读上下文条 + hidden input（模板层一次编写，全模型复用）。
- 安全：字段名白名单（id 类字段才可预置，title/content 等自由字段永不接受 URL 预置）；值唯一不可伪造（服务端覆写）；不改审核语义（status 仍由审核开关定）。

**问答频道效果**：问题详情页「我来回答」→ `/ucenter/submit/answers?question=${info.id}` → 表单顶部显示"回答问题：{问题标题}"（只读）→ 提交自动归属。

## 4. X2 内容所有者操作（采纳/编辑/下架自己的内容）

**能力定义**：登录用户对 **user_id=自己** 的内容行，可更新**模型级白名单字段**；目标行不存在或非本人 → 拒绝。

**设计**：
- `POST /ucenter/content/update`：参数 modelCode/id/字段键值；校验链 = 模型存在且启用 → 行存在 → `row.user_id == 当前用户`（唯一所有权依据，管理员走 modeldata 不走此通道）→ 字段白名单。
- 字段白名单口径（复用既有语义，不加新列）：**该模型 is_form=1 且非 relate 的自定义字段 + accepted 这类状态字段**。更精确的做法是给 fly_model_field 加一个「所有者可改」开关——但为控制本期范围，一期用 `is_form=1` 口径（能投稿就能改自己的），文档注明可升级为独立开关。
- 状态字段特殊规则：status（审核态）不可经此通道修改（防绕审核）；下架需求用行内 `self_status` 语义？——**一期收敛为：只支持自定义字段更新（采纳=改 answers.accepted），status 一律走审核流**，避免与审核语义打架。
- 前台交互：问题详情页模板对「提问者本人」渲染"采纳"按钮（模板可用 fly_login 比对 info.userId——**行数据 user_id 需在行 Map 里**：确认读侧有 userId 键（固有列 normalizeKeys 已带 userId），模板 `${info.userId == status.userId}` 判断）→ 提交 X2 通道改 accepted → 列表按 `accepted=已采纳`（is_filter）置顶段渲染。
- 探针：非本人改 → 拒绝；本人改白名单字段 → 成功；改 status → 拒绝。

## 5. X3 通知动作扩展（可选，二期）

G17 自动化规则（`fly_automation_rule`）新增动作类型 `notify`：event=insert + model_code=answers 时，向目标行的 user_id 发站内信（站内信基础设施若缺则先落 log 动作 + 站内信表单独立项）。规则全部后台配置，零代码。本期不阻塞问答闭环。

## 6. 问答频道完整组装配方（管理员视角，零 Java 代码）

**第 1 步 模型（已就绪）**：questions（title/分类/悬赏 weight/enable_submit✓）+ answers（question relate / accepted radio「待采纳,已采纳」is_filter=1 / enable_submit✓）。唯一要在后台补的动作：给 answers.question 勾「列表筛选」、新建 accepted 字段。

**第 2 步 模板**（模板管理后台维护，属"配置"）：

| 页面 | 模板 | 标签编排 |
|---|---|---|
| 频道首页 | questions/index 或复用 list | `<@fly_category_model model="questions">` 分类条 + `<@fly_page_model model="questions" orderby="id" order="desc">` 最新问题列表（行内 `${(row.questionBacks)![]?size}` 显示回答数）+ 侧栏 `<@fly_list_model model="questions" rows="10">` 高悬赏 |
| 问题详情 | detail-questions.html | `${info.title}` + 正文；回答列表两段：`<@fly_list_model model="answers" question="${info.id}" accepted="已采纳">` 置顶采纳区 + `<@fly_list_model model="answers" question="${info.id}">` 全部回答；`<@fly_login>` 比对 userId 渲染「我来回答」(`/ucenter/submit/answers?question=${info.id}`) 与「采纳」按钮（X2） |
| 回答表单 | submit-answers.html | `meta.fixed` 只读上下文条（X1）+ 正文控件 |
| 提问表单 | submit-questions.html | 常规投稿表单 + 悬赏数字字段 |
| 个人中心 | ucenter 页 | `<@fly_login>` + `<@fly_page_model model="questions" userId="${status.userId}">` 我的提问 / 同理 answers 我的回答 |

**第 3 步 流程开关**：`fly_article_audit=1` 时回答先审后显；分类在「模型列表→分类」抽屉维护（questions 专属分类树，导航/筛选直接可用）。

## 8. 不做清单

- **「多表模型」新对象**：relate + 编排已覆盖（§2），发明新概念只会重复 E1 并引入级联/权限派生复杂度；
- **问答专属硬编码**（悬赏冻结/采纳自动结算等交易语义）：积分核扣属交易系统后置（§13.5 配方既有口径），用 number 字段表达悬赏即可；
- **前台免审核直接采纳生效**：采纳动作一期不绕审核流（status 不可经 X2 修改）；被采纳回答若尚在待审，随审核通过自然展示；
- **匿名提问/回答**：投稿通道已有登录语义（未登录 404/拒绝），保持。
