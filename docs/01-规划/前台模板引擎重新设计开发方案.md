## 一、现状盘点：我们已经有什么

重新设计不是推倒重来。先摸清家底，避免重复造轮子。

### 1.1 已落地的能力

| 能力 | 实现位置 | 状态 |
|---|---|---|
| 模板在线编辑（读/写/建/删） | `ApiWebsiteController` + `TemplateCenterService` | ✅ 已落地 |
| 版本快照与回滚 | `TemplateCenterService.save/restore` + `fly_template_file/version` | ✅ 已落地 |
| 皮肤包导入导出（zip + manifest） | `TemplateCenterService.exportSkin/importSkin` | ✅ 已落地 |
| 保存前 FreeMarker 语法校验 | `validateSyntax()` | ✅ 已落地 |
| 试渲染（不落盘预览） | `preview()` + `sampleModel()` | ✅ 已落地 |
| 在线标签手册 | `TagManualService`（文档与代码同源） | ✅ 已落地 |
| 模板安全沙箱 | `FreemarkerSandboxConfig`（禁 `?new`） | ✅ 已落地 |
| 模板标签族 | `web/tags/` 48+ 个 `<@fly_xxx>` 自动注册 | ✅ 已落地 |
| 自定义模型动态模板解析 | `ModelController.resolveTemplate` | 🟡 三级回退 |
| 栏目模板解析 | `ChannelRenderService.resolveTemplate` | 🟡 三级回退 |
| 前台主题切换 | `fly_config_web.pc_theme` 单键 | 🟡 仅换目录名 |

### 1.2 六个真实痛点

**痛点 1：模板解析逻辑三处重复，且各写各的**

```
ModelController.resolveTemplate      → 自定义模板 → {code}/{type} → cmodel/{type}
ChannelRenderService.resolveTemplate → 栏目模板 → 模型模板 → cmodel/channel
TemplateService.getPcTemplate        → 只拼路径，不做回退
```

同一个"该用哪个模板"的问题，三处答案。新增一种页面类型（如搜索页、标签页）要改三处，
行为必然漂移。**缺一个统一的模板解析器**。

**痛点 2：没有模板层级，只有三级硬回退**

WordPress 能做到"给 ID 为 42 的文章单独套一个模板"，靠的是层级命名
（`page-{slug}.php` → `page-{id}.php` → `page.php` → `index.php`）。
FlyCms 现在只有 `{code}/list`、`{code}/detail`、`cmodel/list` 三级，
**无法做"某栏目用专属模板""某条内容用专属模板"这类精细覆盖**，只能靠复制整个目录。

**痛点 3：子主题不存在，"新建皮肤"是全量复制**

`createSkin(skin, from)` 是 `copyDir` 全量复制。父主题修了个 XSS，子主题永远收不到。
WordPress 的答案是**同名覆盖 + 其余回退父主题**：子主题只放改动过的文件。

**痛点 4：主题没有元信息，切换是"盲切"**

`listSkins()` 只返回目录名字符串。后台看不到主题名、版本、作者、缩略图、
**更不知道这个主题缺哪些模板**。切过去前台可能白屏，且没有一键回滚。

**痛点 5：换肤 = 改配置键，没有事务与预览**

`pc_theme` 是个字符串配置。切换没有：兼容性预检、预览（自己看新的、访客看旧的）、
失败自动回滚。生产环境换主题是高风险操作，现在没有任何保护。

**痛点 6：模板复用靠 `<#include "../common/header.html">` 硬编码**

路径写死在模板里，后台无法管理"模板部件"。想让某个栏目换个 header，只能改模板文件。
帝国 CMS 的"碎片"、WordPress 的 "template parts" 都是把这个变成后台可配对象。

## 二、业界调研：四家 CMS 的模板设计精髓

### 2.1 WordPress：三大支柱

**支柱一：模板层级（Template Hierarchy）**

核心是三句话：**最具体的优先；命中即停；`index.php` 兜底**。

| 请求类型 | 候选模板（左→右，第一个存在的胜出） |
|---|---|
| 首页 | `front-page.php` → `home.php` → `index.php` |
| 单篇文章 | `single-{type}-{slug}.php` → `single-{type}.php` → `single.php` → `singular.php` → `index.php` |
| 静态页面 | `{后台指定的模板}` → `page-{slug}.php` → `page-{id}.php` → `page.php` → `index.php` |
| 分类归档 | `category-{slug}.php` → `category-{id}.php` → `category.php` → `archive.php` → `index.php` |
| 标签归档 | `tag-{slug}.php` → `tag-{id}.php` → `tag.php` → `archive.php` → `index.php` |
| 作者归档 | `author-{nicename}.php` → `author-{id}.php` → `author.php` → `archive.php` → `index.php` |
| 搜索结果 | `search.php` → `index.php` |
| 404 | `404.php` → `index.php` |

**关键设计**：后台给某条内容指定的模板（Page Template 下拉）**永远排在最前**。
这让"运营想让这个落地页不一样"变成一次下拉选择，不需要懂文件名。

**支柱二：子主题（Child Theme）**

- 子主题里放同名文件即覆盖父主题，**其余全部回退父主题**；
- `style.css` 头部写 `Template: 父主题目录名` 声明继承关系；
- `functions.php` 特殊：**父子都加载**（子先加载），不是覆盖——因此改父主题行为要用钩子，不能复制文件；
- 原则：**只复制真正要改的文件**。每多复制一个文件，就多一个不再接收父主题安全修复的文件。

**支柱三：theme.json + 站点编辑器（FSE）**

- `theme.json` 声明主题的设计系统：调色板、字号阶梯、间距、布局宽度、每区块默认样式；
- WordPress 把它编译成 CSS 自定义属性（`--wp--preset--color--primary`）；
- 站点编辑器（Site Editor）所见即所得地改模板/模板部件/全局样式；
- **用户在站点编辑器里的改动存数据库（`wp_template` 文章类型），优先级高于磁盘文件**——
  这是"后台改模板不碰文件"的关键；
- 模板部件（parts/）：header/footer/sidebar 成为可独立编辑、可复用的区域；
- 区块图案（patterns/）：可插入的预设布局组合。

> ⚠️ WordPress 自身的教训：模板存 DB 后，站点结构依赖数据库完整性，
> 拿到编辑权限就能改全站布局，攻击面比"只读文件"大。**FlyCms 必须配套权限收敛 + 版本留痕。**

### 2.2 Drupal：模板建议与区域

- **模板建议（theme hook suggestions）**：渲染节点时按
  `node--{id}--{viewmode}.html.twig` → `node--{id}.html.twig` → `node--{type}--{viewmode}.html.twig`
  → `node--{type}.html.twig` → `node.html.twig` 从最具体到最通用查找；
- 模块、主题引擎、主题**各层都能用 hook 追加/修改建议列表**——这是可插拔的关键：
  `hook_theme_suggestions_HOOK_alter()`；
- **区域（regions）**：主题在 `.info.yml` 声明区域（header/content/sidebar/footer），
  后台把区块（block）拖进区域——**布局是配置，不是代码**；
- 教训：改模板必须清缓存，否则不生效。FlyCms 要在保存时主动失效缓存（现已做）。

### 2.3 Joomla：模板覆盖（Override）

- 模板可以在自己的 `html/` 目录下放同名文件覆盖任何组件/模块的视图；
- 后台"模板管理"可创建覆盖，改动与核心隔离；
- 借鉴点：**覆盖是"同名文件优先"的通用机制**，不限于模板层级。

### 2.4 国产 CMS：织梦 DedeCMS / 帝国 CMS

| CMS | 模板设计 | 可借鉴 |
|---|---|---|
| 织梦 | 模板分四类：**封面（index_*.htm）、列表（list_*.htm）、内容（article_*.htm）、其它（search/RSS）**；标签按作用域分**全局/列表/内容/模块**四类；栏目后台直接填"列表模板""文章模板"路径 | ① 页面类型分类清晰；② **标签按作用域分类**（哪些标签只能在列表页用，一目了然）；③ 栏目绑模板的后台交互 |
| 帝国 | **灵动标签**（`e:loop`，可写 SQL 取数）、**碎片管理**（页面上"一块会变的内容"抽象成后台对象）、**方案管理**（模板组）、参数白名单式安全设计 | ① 碎片/推荐位（FlyCms 阶段 E 已做）；② 灵动标签的灵活度；③ 白名单安全 |
| PHPCMS | 栏目页/列表页/详情页三级模板分离清晰；缓存层次设计 | 三级模板分离 + 缓存分层 |

> 三家老 CMS 的**死因不是功能不够，是模式落后**：模板直写不可回滚、标签方言学不会、
> 升级毁站、停更收费。FlyCms 要学它们的方法论，但实现必须是现代架构。

### 2.5 现代方案

## 三、设计目标与原则

### 3.1 一句话目标

> **换主题 = 点一下；改模板 = 选一下；加页面 = 建一个文件；写模板 = 点组件。**

### 3.2 五条原则

| # | 原则 | 具体含义 |
|---|---|---|
| P1 | **文件系统仍是事实源** | 磁盘上的模板始终可渲染，FTP 手改依然有效。DB 覆盖层是**增强**，不是替代。避免 WordPress "模板存 DB 后站点依赖数据库完整性"的坑 |
| P2 | **层级优于配置** | 能靠"文件名更具体"解决的，不加配置字段。配置只用于层级无法表达的场景（如"这条内容强制用某模板"） |
| P3 | **最具体优先，命中即停** | 与 WordPress 同构，行为可预测、可调试 |
| P4 | **切换必须可回滚** | 换主题是高风险操作，必须：预检 → 预览 → 原子切换 → 失败自动回滚 |
| P5 | **文档与代码同源** | 标签手册、主题能力声明都从代码/配置推导，不手写文档（现已做，需延续） |

## 四、总体架构

### 4.1 分层

```
┌─────────────────────────────────────────────────────────┐
│ L5 后台交互层   主题市场 / 模板编辑器 / 模板选择器 / 组件面板  │
├─────────────────────────────────────────────────────────┤
│ L4 覆盖与配置层 DB 模板指派(内容/栏目/模型) + 主题全局样式配置 │
├─────────────────────────────────────────────────────────┤
│ L3 解析引擎层   TemplateResolver（唯一模板解析入口）★核心新增  │
├─────────────────────────────────────────────────────────┤
│ L2 主题注册表   ThemeRegistry（theme.json + 父子继承 + 元信息）│
├─────────────────────────────────────────────────────────┤
│ L1 存储层       磁盘 skins/ 目录树 + fly_template_* 版本留痕  │
└─────────────────────────────────────────────────────────┘
```

### 4.2 三个核心组件（新增）

| 组件 | 职责 | 解决痛点 |
|---|---|---|
| **`TemplateResolver`** | **唯一**的模板解析入口。输入"页面上下文"，输出物理模板路径。三处 `resolveTemplate` 全部废弃，改调它 | 痛点 1 |
| **`ThemeRegistry`** | 扫描皮肤目录、读 `theme.json`、维护父子继承链、提供主题元信息与能力清单 | 痛点 3、4 |
| **`ThemeSwitchService`** | 主题切换的预检、预览、原子切换、一键回滚 | 痛点 5 |

### 4.3 页面上下文（TemplateContext）

解析引擎的输入，取代现在散落的参数传递：

```java
public class TemplateContext {
    PageType pageType;     // INDEX / LIST / DETAIL / SEARCH / TAG / CHANNEL_PAGE / ERROR
    String   modelCode;    // 模型 code，如 articles
    String   channelDir;   // 栏目目录，如 news
    Long     contentId;    // 内容 ID（详情页）
    String   shortUrl;     // 短网址（详情页）
    Integer  errorCode;    // 403/404/500
    Long     assignedId;   // DB 指派的模板 ID（最高优先级）
    Device   device;       // PC / MOBILE
}
```

## 五、模板层级设计（核心）

### 5.1 层级规则

优先级从高到低，**命中即停**。第一优先级恒为"DB 指派模板"（对应 WP 后台 Page Template 下拉）。

#### 首页（INDEX）
```
1. {DB指派}                  ← 后台"网站设置→首页模板"指定
2. index.html
```

#### 列表页（LIST）—— 模型列表 / 栏目列表共用
```
1. {DB指派}                  ← 栏目或模型上指定的模板
2. list-{channel}-{model}.html    栏目+模型组合，最具体
3. list-{channel}.html            栏目级（channel = 栏目目录名）
4. list-{model}.html              模型级（model = 模型 code）
5. list.html                      通用列表
6. index.html
```

> 例：栏目 `news` 绑定模型 `articles`，访问 `/news/` 依次找
> `list-news-articles.html` → `list-news.html` → `list-articles.html` → `list.html` → `index.html`。
> 想让新闻栏目换个版式？**新建 `list-news.html` 即可，其他栏目不受影响**——
> 这正是 WordPress 层级最实用的地方。

#### 详情页（DETAIL）
```
1. {DB指派}                  ← 内容编辑时选的模板
2. detail-{model}-{id}.html       单条内容级
3. detail-{model}-{shortUrl}.html
4. detail-{channel}-{model}.html
5. detail-{model}.html            模型级
6. detail-{channel}.html          栏目级
7. detail.html                    通用详情
8. index.html
```

#### 栏目封面（CHANNEL_PAGE，单页型栏目）
```
1. {DB指派}
2. page-{channel}.html
3. page.html
4. index.html
```

#### 搜索 / 标签 / 错误页（**2026-09-28 起同样支持 DB 指派**，走站点级 `SITE/site`）
```
搜索：  {DB指派} → search.html → index.html
标签：  {DB指派} → tag-{tag}.html → tag.html → index.html
错误：  {DB指派} → {code}.html（404.html/403.html/500.html） → index.html
```

> 上一版本这三类页面**没有** DB 指派——因为 `assignedTemplate()` 当时硬编码只对
> `DETAIL` / `LIST` / `INDEX` 返回值，其余一律返回 null。2026-09-28 改为按 `PageType`
> 枚举直取（枚举值与 `fly_template_assign.page_type` 列一字不差），四类页面**同时**获得指派能力，
> 且以后新增 PageType 不会再漏（详见 §5.3 与执行清单 P2-4）。

### 5.2 命名规范

| 规则 | 说明 |
|---|---|
| 全小写，单词用 `-` 连接 | `list-news-articles.html`，不用驼峰 |
| 前缀即页面类型 | `list-` 列表、`detail-` 详情、`page-` 单页、`tag-` 标签 |
| 后缀即作用域 | 从具体到宽泛：栏目+模型 → 栏目 → 模型 → 通用 |
| 保留名 | `index.html`（兜底）、`404/403/500.html`、`search.html` |
| 子目录仍可用 | 兼容现有 `{code}/list.html`，但**推荐平铺命名**以启用层级 |

> **兼容策略**：现有 `articles/list.html`、`cmodel/list.html` 继续有效，
> 作为层级末端的额外候选加入回退链，**存量模板零改动即可运行**。

### 5.3 DB 覆盖层（借鉴 WP 的 `wp_template`）

WordPress 把站点编辑器的改动存 DB 并优先于磁盘文件。FlyCms 采用**更保守的变体**：

- DB 只存**模板指派关系**（"这条内容用哪个模板"），**不存模板正文**；
- 模板正文仍在磁盘 → 保住 P1（文件系统是事实源），避免"站点结构依赖数据库"；
- 版本历史继续走现有 `fly_template_version`，用于回滚而非覆盖渲染。

```sql
-- 模板指派：谁用了哪个模板
CREATE TABLE fly_template_assign (
  id          BIGINT AUTO_INCREMENT PRIMARY KEY,
  target_type VARCHAR(20) NOT NULL COMMENT 'CONTENT/CHANNEL/MODEL/SITE（注意：无 CATEGORY）',
  target_id   VARCHAR(64) NOT NULL COMMENT '见下方口径表',
  page_type   VARCHAR(20) NOT NULL COMMENT 'DETAIL/LIST/INDEX/CHANNEL_PAGE/SEARCH/TAG/ERROR',
  template    VARCHAR(200) NOT NULL COMMENT '模板相对路径，如 index.html / detail-articles.html',
  create_time DATETIME
) COMMENT='模板指派表';
```

#### `target_id` 口径（2026-09-28 定稿，代码与文档以此为准）

**一律用「目录名 / code 这类稳定标识」，不用自增 ID。** 理由：栏目重建、模型导出再导入后
数字 ID 会漂移，而目录名与模型 code 与前台路由一一对应，永远不会对不上。

| `target_type` | `target_id` 取值 | 示例 | 说明 |
|---|---|---|---|
| `CONTENT` | 内容**数字 ID** | `1234` | 内容不会被重建，ID 稳定，可直接用 |
| `CHANNEL` | 栏目**目录名** | `news` | 与前台路由 `/news` 一致；**不是**栏目表的主键 ID |
| `MODEL` | 模型 **code** | `articles` | 与 `/articles/` 路由、`fly_cmodel_articles` 表名一致 |
| `SITE` | 固定字符串 `site` | `site` | 站点级兜底，承载首页 / 搜索 / 标签 / 错误页的指派 |

#### 查询优先级（由具体到宽泛，命中即返回）

`CONTENT(id)` → `CHANNEL(目录名)` → `MODEL(code)` → `SITE('site')`

#### `page_type` 七种枚举

`PageType` 枚举值与 `fly_template_assign.page_type` 列**一字不差**，代码里用
`ctx.getPageType().name()` 直取即可查库，不再写 `if/else` 分支——这样**新增页面类型不会再漏掉指派能力**
（早期只给 `DETAIL/LIST/INDEX` 返回值，导致单页栏目、搜索页、标签页、错误页的指派**静默失效**，
见《模板引擎补齐执行清单》P2-4）。

### 5.4 解析器实现要点

```java
public String resolve(TemplateContext ctx) {
    List<String> candidates = buildCandidates(ctx);   // 按上表生成候选名
    for (String name : candidates) {
        File f = locate(ctx.getSkin(), name);          // 先子主题，后父主题
        if (f != null && f.isFile()) return viewName(f);
    }
    return viewName(locate(ctx.getSkin(), "index.html"));  // 兜底
}
```

- **候选表生成与主题配置解耦**，新增页面类型只改 `buildCandidates` 一处；
- **定位走 `ThemeRegistry`**，自动处理子主题回退父主题；
- **解析结果记 debug 日志**，并提供后台"模板调试"开关（前台输出 HTML 注释标明用的是哪个模板）
  —— 对应 WordPress 的 Query Monitor，解决"为什么这个页面用的是这个模板"。

### 6.2 子主题继承


### 6.4 主题切换的安全事务（痛点 5 的完整解法）

```
1. 预检   ThemeRegistry.checkCompatibility(newSkin)
          → 输出：缺失模板清单、版本不兼容、父主题缺失
          → 有 BLOCK 级问题则拒绝切换并给出原因
2. 快照   记录 currentSkin、当前配置
3. 切换   写 pc_theme（原子）→ 清 FreeMarker 缓存 → 清页面缓存
4. 前置校验 快照拿到的"当前主题"必须是磁盘上真实存在的主题，否则中止切换、不写任何配置
            （否则写进 pc_theme_prev 的是脏回滚点，"一键回滚"会就此永久失效）
5. 探活   自请求 127.0.0.1:${server.port} 的首页（硬性）与第一个可见列表栏目页（软性，仅告警）
          判定：非 200，**或**返回 200 但响应体含 "FreeMarker template error"
          （FreeMarker 的 DEBUG 异常处理器会把模板报错内联进页面、状态码仍是 200，只看状态码必漏判）
          请求未到达应用（连接拒绝/超时）时 fail-open：不回滚、只告警 —— 避免探活自身故障
          导致任何主题都切不上去，那比不做探活更糟
6. 回滚   自动切回上一个主题，回滚后**再探一次**确认服务真的恢复；若仍失败则升级为"请立即人工介入"
```

## 七、模板部件：让"改一块"不动"整页"

### 7.1 三类可复用单元

| 类型 | 对应 | 存储 | 后台可管 | 典型用途 |
|---|---|---|---|---|
| **模板部件** | WP `parts/` | `skins/{skin}/parts/*.html` | ✅ 列出/编辑/版本 | 页头、页脚、侧边栏 |
| **碎片/推荐位** | 帝国碎片 | `fly_block`（**已落地**） | ✅ 完整管理 | 首页"本周热盘"、广告位 |
| **区块图案** | WP `patterns/` | `skins/{skin}/patterns/*.html` | ✅ **已落地（2026-09-28）**：列出/预览/搜索/一键插入 | 预设的图文组合、CTA 区 |

> **图案文件怎么写**：图案本身就是一段可直接插入的 FreeMarker 片段，元信息写在文件**首行注释**里
> （`@name` 显示名 / `@desc` 描述），后台列表即读这里。示例 `patterns/cta-banner.html`：
>
> ```freemarker
> <#-- @name 图文两栏 CTA
>      @desc 左图右文 + 主按钮，适合栏目页顶部引导 -->
> <section class="cta"> ... </section>
> ```
>
> 读取接口对 `file` 参数做路径逃逸防御（必须落在本主题 `patterns/` 下，`../evil.html` 一律拒绝）。

### 7.2 部件引入标签

现有硬编码 `<#include "../common/header.html">` 保留兼容，新增部件标签：

```freemarker
<@fly_part name="header"/>          <!-- 自动按 子主题→父主题 查找 parts/header.html -->
<@fly_block key="home_focus"/>      <!-- 已有：碎片 -->
```

**收益**：部件路径不再写死，换父主题/子主题覆盖自动生效；后台"模板部件"页可直接编辑页头页脚。

### 7.3 区域（Regions）—— 借鉴 Drupal 的中期目标

主题在 `theme.json` 声明区域，后台把区块放进区域，**布局成为配置**：

```json
"supports": { "regions": ["content_top", "sidebar", "content_bottom"] }
```

```freemarker
<@fly_area name="content_top">默认内容</@fly_area>
```

> **2026-09-28 已落地（P10）**，与本节原设想的两处差异：
> ① 区域声明实际在 **`supports.regions`**（与 `supports.templates` / `supports.parts` 同级），
> 不是顶层 `regions`——这样区域和能力声明收在同一个命名空间里；
> ② 后台"布局管理"页用的是**列表式编排**（选区域 → 放区块 → 上移/下移/启停），**不是拖拽**。
> 拖拽属 §14 的 V3，见 §17.3 未做清单第 4 项。
>
> 区块支持三态：`BLOCK`（引用 `fly_block` 碎片）/ `TAG`（直接写标签调用）/ `HTML`（纯片段），
> 且提供 iframe 实时预览（`srcdoc` + `sandbox=""`，脚本不执行）。

## 九、标签体系：模板怎么取数据

### 9.1 现有基础

48+ 个 `<@fly_xxx>` 标签（**2026-09-28 精确点数为 55 个**），`AbstractTagPlugin` 按类名自动注册

> ⚠️ **注册名规则（2026-09-27 踩坑入库，2026-09-28 修正表述）**：`AbstractTagPlugin.init()`
> 按 `fly_` + bean 名注册，转换规则是 **`StringHelperUtils.toUnderline`——只在大写字母前加下划线，
> 并不拆驼峰**。所以：
>
> | 类名 | 注册名 | 常见误写（都会导致 `evaluated to null or missing`） |
> |---|---|---|
> | `PageModel` | `fly_page_model` | — |
> | `ListModel` | `fly_list_model` | — |
> | `Articlepage` | `fly_articlepage` | ~~`fly_article_page`~~ |
> | `Answerpage` | `fly_answerpage` | ~~`fly_answer_page`~~ |
> | `Dateformat` | `fly_dateformat` | ~~`fly_date_format`~~ |
> | `Stringcut` | `fly_stringcut` | ~~`fly_string_cut`~~ |
> | `Areaslist` | `fly_areaslist` | ~~`fly_areas_list`~~ |
>
> **自查姿势**：不要凭"英文词组"脑补下划线。写模板前先调 `GET /api/system/tags/manual`
> 拿真实注册名，或直接看 `AbstractTagPlugin` 的注册逻辑。
> （在线标签手册原先把 `fly_article_page` 之类的臆想名写进骨架代码，照着"插入"必然报错，
> 已于 2026-09-28 全量对齐源码：55/55 零偏差，见《模板引擎补齐执行清单》P3-4。）
>
> ⚠️ 模板里写裸类名 `<@InfoModel>` 会报 "evaluated to null or missing"；且 FreeMarker DEBUG 模式
> 会把模板报错**内联输出成 HTTP 200 页面**——静态化会把错误页当快照忠实写盘。
> 验证前台渲染必须 grep 关键内容（`FreeMarker template error`），不能只看状态码/体积。
>
> ⚠️ **模型数据 Map 的类型陷阱（同日第二坑）**：`resultType="map"` 的行里
> DATETIME 列到模板是 **ISO 字符串**（`2026-09-21T05:55:28`，带 T）——格式化用
> `?replace("T"," ")?substring(0,16)`，**不能用 `?string(pattern)`**（那是日期
> 对象专用，字符串会抛 "Expected a method or function"）；bigint/int 列是
> **数字**——判空不能写 `v != ''`（两类型比较直接抛异常），要先 `?is_string`
> 再比内容，或只判 `??`。

> **`?string(` 的正确自查姿势（2026-09-28 复核，修正上一版"无残留"的笼统表述）**
>
> 全文 grep `?string(` 会命中 **13 处**，其中**没有一处是真缺陷**。原因是 FreeMarker 里
> `?string` 有**三种互不相干的用法**，只有第三种才是坑：
>
> | 用法 | 形态 | 是否安全 | 本仓命中 |
> |---|---|---|---|
> | **日期格式化** | `someDate?string('yyyy-MM-dd HH:mm:ss')` | ✅ 只要目标确实是 `java.util.Date` | 6 处：`article/detail.html:40,101`、`share/detail.html:48`、`user/account.html:123`、`user/account_log.html:72`、`user/invite.html:70`（分别是 `Article` / `ArticleComment` / `Share` / `User.birthday` / `ScoreDetail` / `UserInvite` 的字段，**全是 `Date`**） |
> | **布尔内置** | `(cond)?string(a, b)` | ✅ 与日期无关，是三元表达式 | 4 处：`article/index.html:43,49`、`search.html:9`、`search/detail.html:8` |
> | **数字格式化** | `someNumber?string('0.00')` | ⚠️ 目标必须是数字 | 0 处 |
> | **对 map 行的字符串用 `?string(pattern)`** | `row.createTime?string('...')` 而 `row` 是 `resultType="map"` | ❌ **真坑**，必抛异常 | **0 处（已清零）** |
>
> 另有 2 处是**注释里提到这个写法**（`articles/detail.html:21`、`common/macros.html:4`），
> 以及 1 处 `.now?string("hhmmSSsss")`（`.now` 是日期，安全）。
>
> **结论**：新版平铺模板已无第三种用法；存量老模板命中前两种是**正确写法，不要"顺手改掉"**。
> 复核时请按上表分类判断，不要只看 grep 计数。

## 十、缓存与性能

现在 `spring.freemarker.cache: false`（开发期配置），生产必须打开。

**2026-09-28 落实方式：按 profile 分流，而不是二选一。** 开发期 `cache: false` 是刻意的——
后台在线改模板要"保存即可见"，关缓存最省心；生产才需要编译缓存扛吞吐。两者诉求相反，
所以用 `spring.config.activate.on-profile: prod` 覆盖而不是改默认值：

| profile | `freemarker.cache` | `template_update_delay` | `devtools` |
|---|---|---|---|
| 默认（dev） | `false` | `0` | 按需 |
| `prod` | `true` | `0` | `false` |

启动：`--spring.profiles.active=prod`。

| 层 | 方案 | 失效时机 |
|---|---|---|
| **模板编译缓存** | `cache: true` + `template_update_delay: 0` | 保存模板时主动 `removeTemplateFromCache`（**已实现**） |
| **主题清单缓存** | Caffeine 缓存 `ThemeRegistry` 扫描结果 | 主题增删改、theme.json 变更时清 |
| **模板解析结果缓存** | 缓存"上下文 → 模板路径"，避免每次请求遍历候选链 | 同上 + 模板文件增删 |
| **页面片段缓存** | 碎片 `fly_block` 渲染结果缓存 | 碎片变更时清 |
| **整页静态化** | 远期：列表/详情页生成静态 HTML | 内容发布时刷新 |

> 注意 WordPress 的教训：**改了不生效是最伤用户信心的 bug**。
> 所有缓存失效必须走统一入口，且后台提供"**清空模板缓存**"按钮兜底。

### 17.4 关键实现笔记（供后续参考）
- Spring Boot 4 用 **Jakarta**（`jakarta.servlet.*`），不是 `javax.servlet.*`；FreeMarker 视图名**不能带** `.html`（resolver 会再补一次后缀）。
- `ThemeRegistry.locate` 返回**不带** `.html` 的视图名；`locate` 内部会先剥掉输入里的 `.html`，所以传入带后缀或不带后缀都能命中——但**回填给调试条的 `resolvedFile` 必须统一归一化**，否则会出现 `index.html.html`（2026-09-28 修复，§13 #43）。
- `?__skin` 预览：解析结果有 60s 缓存，`activeSkin()` 在预览主题不在缓存时强制 `refresh()`。
- Maven 编译堆：`-Xmx1024m` 可编译；整 JVM 启动若 fork 2GB 会 OOM，改单 JVM 运行 `java -Xmx1024m -cp "target/classes;$(cat target/cp.txt)" com.flycms.Application`。
- stage-j 权限 id 900180–900182 与「站内短信」冲突（`INSERT IGNORE` 跳过），故补 stage-j2 用 900188/900189/900193。
- **菜单装配必须用递归（2026-09-27 教训）**：C 菜单下再挂 C 菜单属"孙子节点"，旧版两级装配会无声丢弃——
  主题市场页"已落地却看不见"即此因，SQL 执行成功 ≠ 菜单真的渲染。新增页面后必须
  curl `/api/menu/all` 确认节点出现在路由树里才算闭环（stage-o 修复，§13 #26）。
- **转发不携带状态码（2026-09-28 教训）**：`return "forward:/404"` 只是内部转发，
  HTTP 状态码由**最终执行的那个 handler** 决定。错误页处理器不加 `@ResponseStatus`，
  全站"页面不存在"就都是 **200**——搜索引擎收录、监控告警、CDN 缓存策略全部失效。
- **`@RequestParam` 绑定发生在方法体之前（2026-09-28 教训）**：把参数声明为必需，
  等于把"缺参异常"排在 `requirePermission()` **前面**。未登录请求拿到的是 400/500 而不是 401，
  "未登录一律 401"的约定被无声破坏。凡"先鉴权再校验入参"的接口，参数都要 `required = false`。
- **Spring 6 不匹配尾斜杠**：目录式前台路由必须显式声明 `"/xxx"` 与 `"/xxx/"` 两个 pattern
  （本仓已在 `/tag/{tag}`、`/html/{dir}/` 等处踩过两次）。
- **动态模型表名是 `fly_cmodel_{code}`**：凡拼表名的 SQL 一律用模型 **code**，
  用 `id` 会拼出一张不存在的表——而这类 SQL 常被 `catch` 吞掉，表现是"功能静默不生效"
  而不是报错（2026-09-28 在 sitemap 与定时发布两处同时命中）。
