## 1. 结论摘要

**五个结论。**

1. **全项目内容模块都能收敛，且收敛成本远低于预期。** 实测数据库：`fly_article`、`fly_share`、`fly_question`、`fly_answer`、`fly_article_comment` **全部 0 行**；仅 `fly_topic` 18 行、`fly_user` 1 行是有意义数据。这意味着"迁移风险最大的存量数据"实际上不存在——**收敛退化为"改路由 + 删代码"，而非"搬数据"**。这是本方案最重大的发现，直接改变了实施顺序（见 §2.5）。

2. **文章模块确实不必单独搞。** `articles` 模型已覆盖文章全部内容能力（`source`/`author`/`tags`/`redirecturl` + 独立前台模板 + 16 行真实数据，见 §2.2）。

3. **模型物理表名改为 `fly_cmodel_{code}`。** `fly_cmodel_900000000000000003` → `fly_cmodel_articles`。模型表名应可读可定位，雪花 id 表名是纯信息损耗。

4. **主键：模型元数据改自增，业务数据表保持雪花。** `fly_model` / `fly_model_field` 改 `AUTO_INCREMENT`；`fly_cmodel_*` 业务数据和存量表继续雪花——它们才是并发写入与未来分片的主战场，且保住了 2026-09-24 刚修复的 SnowFlake 单例化成果。

5. **"建任意类型模块"与"模板开箱可调用"是同一件事的两面，靠三个机制达成**（详见 §3、§4）：
   - **字段类型够用**：现有 15 种 `FieldTypeEnum` 覆盖 90% 场景，但缺"多值引用/关联/树形/JSON/计算列/版本"6 类，收尾需补（§3.3）；
   - **标签统一**：把现有 7 个模型标签（`InfoModel`/`ListModel`/`PageModel`/`CategoryModel`/`RelModel`/`HotModel`/`FieldsModel`）收敛为**一个通用标签族**，参数统一、语义一致（§2.3）；
   - **新建即用**：模型创建时**自动注入标签用法注释到生成的模板骨架**，让"新建模块 → 打开模板 → 看到可用标签与示例"闭环（§7.4）。**这是当前最大的缺失，也是本方案的核心增量。**

**一个必须接受的代价**：`code` 从此**永久锁定**（既是 URL 目录名，又是物理表名），必须在创建表单上显著警告。

---


**一个必须接受的代价**：`code` 从此**永久锁定**（既是 URL 目录名，又是物理表名）。现有实现本来也已锁定 `code`（`ModelService.updateModel` 里 `form.setCode(old.getCode())`），本次改动只是把"锁定"的后果从"路由变更"升级为"要改表名"，所以必须在创建表单上把这条警告写清楚。

## 2. 全项目模块收敛评估

### 2.1 实测数据基线（`E:\mysql57`，库 `flycms`）

72 张 `fly_` 表中，**内容类表几乎全空**。这是评估收敛可行性的决定性事实：

| 表 | 行数 | 用途 | 收敛判定 |
|---|---|---|---|
| `fly_article` | **0** | 文章主表 | ✅ 可直接收敛（无数据要迁） |
| `fly_article_category` | 38 | 文章分类（MyISAM） | ⚠️ 需迁分类 |
| `fly_article_category_merge` | 0 | 文章-分类关联 | ✅ 无需迁 |
| `fly_article_comment` | **0** | 文章评论 | ✅ 无需迁，但功能要保 |
| `fly_article_count` / `fly_article_votes` | 0 | 计数/投票 | ✅ 无需迁 |
| `fly_share` | **0** | 分享主表 | ✅ 可直接收敛 |
| `fly_share_category` | 16 | 分享分类（MyISAM） | ⚠️ 需迁分类 |
| `fly_share_comment` / `fly_share_count` / `fly_share_votes` / `fly_share_order` | 0 | 分享周边 | ⚠️ 涉及交易/评论，见 §2.3、D11 |
| `fly_question` | **0** | 问答主表 | ✅ 可收敛主体 |
| `fly_answer` / `fly_answer_count` / `fly_answer_votes` / `fly_question_follow_merge` | 0 | 回答/投票/关注 | ⚠️ 见 §2.3（问答双实体） |
| `fly_topic` | **18** | 话题 | ⚠️ 有数据，需迁移（唯一有量内容表） |
| `fly_topic_*`（6 张） | 0 | 话题周边 | ✅ 无需迁 |
| `fly_user` | 1 | 会员 | ❌ **不收敛**（见 §2.3） |
| `fly_cmodel_900000000000000003` | **16** | `articles` 模型数据 | 已在新体系 |
| `fly_cmodel_900000000000000002` | 2 | `downloads` 模型数据 | 已在新体系 |
| `fly_cmodel_900000000000000001` | 0 | `images` 模型数据 | 已在新体系 |
| `fly_cmodel_1299270553286488064` | 2 | `testdemo` 测试模型 | 🗑️ 建议删除 |
| `fly_channel` | 0 | 统一栏目树 | 待用（规划阶段 C） |

**核心判断**：**除 `fly_topic`(18行) 与分类表（38+16 行）外，没有任何内容数据需要迁移。** v1.0 方案 §10.2 初稿设计的"文章数据迁移"（含分类 ID 映射表、`short_url` 唯一性校验、`count_comment` 归零）**实际不需要执行**——这大幅降低了收敛风险与工作量。

### 2.2 模块逐个评估

| 模块 | 现有实现 | 收敛可行性 | 结论 |
|---|---|---|---|
| **文章 article** | 表 + `ArticleAdminController`(267行) + `ArticleController` + 5 标签 + 旧后台页 | **高** | ✅ `articles` 模型已完全覆盖，且已有 16 行真实数据。**直接切换前台路由，删旧代码** |
| **分享 share** | 表 + `ShareAdminController` + `ShareController` + `Sharepage`/`Shareinfo` 标签 | **中高** | ✅ 主体可收敛为 `shares` 模型；`needmoney`（下载需积分）映射为 `number` 字段；`downloads`（附件）映射 `files`。⚠️ **`fly_share_order` 涉及积分交易，不在内容模型范围** |
| **问答 question/answer** | 表 + `QuestionAdminController` + `AnswerAdminController` + 4 标签 | **中** | ⚠️ **双实体结构**（问题 + 回答），模型系统是单实体。见 §2.3 |
| **话题 topic** | 表 + `TopicsController` + 4 标签，**18 行数据** | **中高** | ⚠️ 字段名非标准（用 `topic` 而非 `title`，无 `keywords`），需字段映射。见 §2.4 |
| **品牌 brand** | `module/brand` + `BrandAdminController` | **高** | ⚠️ **库中无 `fly_brand` 表**（实测 `SHOW TABLES LIKE 'fly_brand%'` 为空）——模块代码存在但表未建，属半成品，直接收敛 |
| **招聘 job** | `fly_job` 实为 **Quartz 定时任务表**（`bean_name`/`cron_expression`） | **不适用** | ❌ 与"内容模块"无关，是基础设施表。`JobAdminController` 保留 |
| **专题 / 聚合** | `fly_topic` 偏社区话题 | **高** | ✅ 由规划文档阶段 C 的"聚合栏目"承接（`channel_type=3`），无需独立模块 |
| **会员 user** | `fly_user` + 15 张关联表 | **不收敛** | ❌ 见 §2.3 |
| **权限/日志/配置** | admin 系 6 表 | **不收敛** | ❌ 平台基础设施，非内容 |

### 2.3 明确不收敛的模块（边界）

| 模块 | 不收敛理由 |
|---|---|
| **会员体系**（`fly_user` + 积分/粉丝/邀请/收藏/消息 15 张表） | 涉及登录态、积分账本、权限、隐私，是**平台基础设施**而非内容。模型系统只管"内容"，不该管"账号"。强行纳入会让模型系统变成第二个 PHPCMS。 |
| **评论**（`fly_article_comment` / `fly_share_comment`） | 评论有**独立的提交/审核/敏感词/通知链路**，且是"多对一"关系（一条内容 N 条评论），与模型"一表一实体"的结构不匹配。**保留为平台能力**，通过 `content_type + content_id` 关联任意模型内容（见 D11 决策）。 |
| **问答 answer** | 问答是**双实体**（问题有多个回答），模型系统是单实体单表。两种处理：① 把"回答"做成独立模型 `answers`，用 `question_id`（number 字段）关联——**推荐**，保持模型系统纯粹；② 给模型系统加"子内容"能力——**否决**，复杂度失控。 |
| **分享订单 `fly_share_order`** | 涉及**积分扣减 + 交易流水**（2026-09-24 刚修复积分符号反转 Bug），属交易系统。内容收敛不影响它，但需保证收敛后 `share` → `shares` 模型的下载动作仍能触发原积分链路。 |
| **定时任务 `fly_job`** | Quartz 基础设施表 |
| **权限/配置** | 平台基础设施 |

### 2.4 话题模块的字段映射（唯一有数据的迁移）

`fly_topic` 18 行是**唯一需要真正迁移的存量内容数据**。其结构与模型标准列差异较大：

| `fly_topic` 列 | 映射到 `fly_cmodel_topics` | 处理 |
|---|---|---|
| `id` | `id` | 直接沿用（雪花） |
| `topic` | `title` | **改名**（模型固有列叫 `title`） |
| `short_url` | `short_url` | 直接沿用 |
| `topic_image` | `thumbnail` | **改名**（已有字段，值为 URL 字符串而非 `fly_images.id`）⚠️ 见下 |
| `content` | `content` | 直接沿用 |
| `count_view` | `count_view` | 直接沿用 |
| `count_num` | `count_comment` | **改名**（语义需人工确认） |
| `count_follow` | 新增 `number` 字段 `count_follow` | 模型加字段 |
| `isgood` | 新增 `number` 字段 `isgood` | 模型加字段 |
| `status` | `status` | 直接沿用 |
| `create_time` | `create_time` | 直接沿用 |

> ⚠️ **`topic_image` 存的是 URL 字符串，而模型的 `thumbnail` 存的是 `fly_images.id`**。这是**两套附件体系的语义冲突**（旧：URL 直存；新：ID 引用 + 引用计数）。迁移时必须：要么把 URL 反查 `fly_images` 拿 id（可能查不到），要么给 `topics` 模型加一个 `input` 字段 `topic_image_url` 存原 URL。**推荐后者**（`fly_images` 实测 0 行，反查必然失败）。这条冲突是"旧模块收敛"的通用坑，见 §10.3。

### 2.5 收敛顺序（据实测数据重排，与原方案不同）

原方案按"文章先做"的顺序。**实测后建议调整**——因为文章表本来就是空的，且 `articles` 模型已有 16 行数据，真正的风险点在话题（有数据 + 字段名不标准）和分享（涉及积分）：

```
第 1 步：表名与主键改造（§7/§8/§9）           ← 纯技术改造，与内容收敛解耦
第 2 步：收敛 article                           ← 零数据迁移，改路由即完成，验证收敛流程
第 3 步：收敛 brand（半成品）+ share 主体       ← 小体量，练手
第 4 步：收敛 topic（18 行真实数据 + 字段映射）  ← 真正的数据迁移演练
第 5 步：收敛 question 主体 + 建 answers 模型    ← 双实体结构
第 6 步：清理旧控制器/旧模板/旧标签              ← 观察期后
```

**第 1 步与第 2 步可并行**（两者改动面不重叠）。

## 3. 万能模型能力评估：能否建任意类型模块

### 3.1 结论

**能建绝大多数类型，但当前有 6 类能力缺口。** 现有 `FieldTypeEnum` 15 种类型 + 固有列 + 动态 DDL，已足以承载"文章/图片/下载/产品/案例/新闻/公告/帮助文档/招聘职位"等**标准内容型模块**。缺口集中在"关系型""结构化数据型""多媒体型"场景。

### 3.2 现有能力盘点（15 种字段类型）

| 分类 | 类型 | 已能承载的模块 |
|---|---|---|
| 文本 | `input` / `textarea` / `editor` | 标题、摘要、正文、富文本 |
| 数值 | `number` / `decimal` | 价格、数量、积分、评分 |
| 时间 | `date` / `datetime` | 发布日期、活动时间、拍摄时间 |
| 选择 | `select` / `radio` / `checkbox` | 状态、分类、多选标签 |
| 附件 | `image` / `images` / `file` / `files` | 封面、图集、附件包、下载包 |
| 地区 | `region` | 地址、地域分类 |
| **固有列** | `title` / `content` / `keywords` / `description` / `thumbnail` / `recommend` / `count_view` / `count_comment` / `status` / `category_id` / `short_url` | 全模型共享的SEO/统计/状态 |

**实测可建的模块举例**（无需任何改造）：产品模型、案例模型、新闻模型、公告模型、帮助文档模型、招聘职位模型、房产楼盘模型、课程模型、人物/团队模型、活动模型。

### 3.3 能力缺口（6 类，按优先级）

| # | 缺口 | 典型场景 | 建议方案 | 优先级 |
|---|---|---|---|---|
| 1 | **关联引用**（relate） | 产品关联品牌、文章关联专题、课程关联讲师 | 新增 `FieldTypeEnum.RELATE`：列存 `fly_cmodel_{target}` 的 id（`bigint`），元数据加 `relate_model` 记录目标模型 code | **P1** |
| 2 | **多选关联**（relates） | 产品关联多个标签、文章关联多个作者 | 同上，JSON 数组列 | **P1** |
| 3 | **树形分类** | 已有 `fly_model_category`，但无"内容自关联成树" | 复用 `category_id`；若需要"内容本身成父子树"，新增 `parent_id` 固有列（可选开启） | P2 |
| 4 | **JSON 结构化字段** | 规格参数（多组键值对）、SKU 列表 | 新增 `FieldTypeEnum.JSON`：列存 JSON，前端用键值对编辑器 | P2 |
| 5 | **计算/公式列** | 折扣价 = 原价 × 折扣、总价 = 单价 × 数量 | 新增元数据 `formula` 表达式，读取时计算（**不落库**） | P3 |
| 6 | **版本/修订** | 文档需保留历史版本 | 复用规划文档阶段 D 的 `fly_template_version` 思路，建 `fly_cmodel_{code}_version` | P3 |

> **为什么"关联引用"是 P1**：它是"把内容组织起来"的最小能力。没有它，模型系统只能建**孤立的**内容表，无法表达"产品属于某品牌""课程由某讲师讲"这类真实关系，这正是"任意类型模块"最常缺的一环。

### 3.4 新增字段类型的实现规格（P1 两项，可直接开发）

**`RELATE`（单值关联）**：

```java
// FieldTypeEnum 新增
RELATE("relate", "bigint(20) unsigned", null),    // 存目标模型内容的 id
RELATES("relates", "json", null);                  // 存 id 数组
```

```sql
-- fly_model_field 新增列（承载关联目标）
ALTER TABLE `fly_model_field`
  ADD COLUMN `relate_model` varchar(32) DEFAULT NULL COMMENT 'RELATE/RELATES 字段的目标模型 code';
```

**校验逻辑**（`ModelDataService.buildDynamicValues`）：

```java
case RELATE: {
    // 1. 取字段元数据 relate_model，查目标模型
    // 2. 校验 id 在 fly_cmodel_{relateModel} 中存在且 status=1
    // 3. 值存 bigint（单值）或 JSON 数组（多值）
}
```

**读取展开**（`ModelDataService.expandAttachments` 的同构逻辑，建议改名 `expandReferences`）：

```java
// 单值关联：row.put(fieldName + "Obj", 目标内容 Map)          → 模板 ${item.brandObj.title}
// 多值关联：row.put(fieldName + "List", 目标内容 List<Map>)   → 模板 <#list item.tagList as t>
```

**前端控件**：新增 `RelatedPicker`（复用 `AttachmentPicker` 的弹窗选择模式，数据源换成 `GET /api/system/modelData/list/{relateModelId}`）。

> **模板零二次查询原则**（沿用模型手册 §7.3）：关联对象必须在 Service 层展开为 `xxxObj` / `xxxList`，模板直接取用，不允许模板内再发查询。

## 4. 模板标签体系设计：新建模块如何开箱可调用

### 4.1 现状诊断（实测）

标签注册机制：`AbstractTagPlugin.init()` 按 `类名 → fly_ + 下划线` 自动注册（`@PostConstruct`）。现有模型标签 7 个：

| 标签 | params | 输出变量 | 用途 |
|---|---|---|---|
| `<@fly_info_model>` | `model`, `id` 或 `shortUrl` | `info` | 详情 |
| `<@fly_list_model>` | `model`, `category`, `title`, `orderby`, `order`, `p`, `rows` + 任意自定义字段筛选 | `dataList`, `model_page` | 列表 |
| `<@fly_page_model>` | 同 `list_model` | `dataList`, `model_page` | 分页列表 |
| `<@fly_category_model>` | `model` | `categoryList` | 分类列表 |
| `<@fly_rel_model>` | `model`, `category`, `notid`, `rows` | `dataList` | 相关内容 |
| `<@fly_hot_model>` | `model`, `rows`, `category` | `dataList` | 热门内容 |
| `<@fly_fields_model>` | `model` | `fieldsList` | 字段元数据 |

### 4.2 现存三个问题（这就是"不够智能"的根因）

**问题 1：`ListModel` 与 `PageModel` 功能重复。** 二者代码 90% 相同，唯一区别是输出变量。模板作者必须记住"要分页用 `page_model`，不要分页用 `list_model`"——这是纯粹的认知负担。

**问题 2：参数解析是"逐个 if 判断"，新增参数要改每个标签。** 每个标签里都有一段：

```java
for (String str : paramWrap.keySet()) {
    if ("model".equals(str)) { modelCode = ...; }
    if ("category".equals(str)) { categoryId = ...; }
    // ...重复
}
```

7 个标签 = 7 份重复代码。**新增一个通用参数（比如 `status`）要改 7 个文件。**

**问题 3（最关键）：新建模型后，模板作者不知道有哪些标签可用。** 模型创建时 `ModelService.generateDefaultTemplates()` 只生成**空骨架** `list.html` / `detail.html`，里面写的标签是硬编码的通用示例，**不含该模型的实际字段名**。运营建了 `products` 模型、加了 `price`/`brand` 字段后，打开模板看到的仍是"用 `${item.title}`"这类通用提示，必须自己查字段名、猜标签参数。

### 4.3 设计目标

1. **标签族收敛**：`list_model` 与 `page_model` 合并，参数统一；
2. **参数解析集中**：抽基类，新增参数只改一处；
3. **新建即用**：模型创建时根据**实际字段**生成带注释的模板骨架，标签用法与字段名都在里面；
4. **前后台一致**：前台标签与后台动态表单用同一套字段元数据，不出现"后台能配、前台不会调"。

### 4.4 改造方案

#### 4.4.1 标签族收敛（问题 1）

**合并 `ListModel` + `PageModel` → `ModelList`**（保留 `fly_list_model` 名称以免破坏现有模板，`PageModel` 标记废弃）：

```ftl
<#-- 新写法：一个标签，自动输出 dataList + pageHtml -->
<@fly_list_model model="products" rows="12" p="${p!1}" orderby="create_time" order="desc">
  <#list dataList as item>
    <a href="/products/${item.shortUrl}.html">${item.title}</a>
  </#list>
  <#-- pageHtml 自动可用，无需区分标签 -->
  <#if pageHtml??>${pageHtml}</#if>
</@fly_list_model>
```

**关键技术点**：现有 `PageVo` 已有 `pageHtml` 能力（`PageModel` 里用），合并后统一输出 `dataList` + `model_page` + `pageHtml` 三个变量，模板按需取用。

#### 4.4.2 参数解析抽基类（问题 2）

新增 `core/base/AbstractModelTag`（继承 `AbstractTagPlugin`），集中承担：

```java
public abstract class AbstractModelTag extends AbstractTagPlugin {

    /** 通用参数（所有模型标签共享） */
    protected static final Set<String> COMMON_PARAMS = Set.of(
            "model", "category", "title", "orderby", "order", "p", "rows", "notid", "status");

    /** 统一的参数解析：返回 Map，未识别参数自动归入 filters（自定义字段筛选） */
    protected TagContext parse(Map params) {
        // 1. model/category/rows/p 等通用参数解析
        // 2. 剩余参数 → filters（供 is_filter=1 字段使用）
        // 3. model = modelService.findModelByCode(code)，null 则短路
    }

    /** 统一的取数封装：模型表不存在时懒补偿，异常时输出空集 */
    protected void renderList(Environment env, TagContext ctx, boolean front) { ... }
}
```

**效果**：7 个标签各减约 30 行重复代码；新增通用参数只改 `COMMON_PARAMS` + `parse()` 一处。

#### 4.4.3 新建模型自动生成"带注释的可用标签骨架"（问题 3，核心增量）

改造 `ModelService.generateDefaultTemplates(model)`：从"写死通用骨架"改为"**读该模型的实际字段，生成定制化模板**"。

生成内容示例（`products` 模型，含 `price`/`brand`/`images` 字段）：

```ftl
<#--
  产品模型 列表页（自动生成于 2026-09-24）
  ═══════════════════════════════════════════════════════════
  本模型可用标签：
    <@fly_list_model>    列表/分页   输出 dataList, pageHtml
    <@fly_category_model> 分类导航   输出 categoryList
    <@fly_hot_model>      热门内容   输出 dataList
    <@fly_rel_model>      相关内容   输出 dataList
  本模型可用字段（共 3 个自定义字段）：
    price   价格       number    ${item.price}
    brand   品牌       relate    ${(item.brandObj.title)!''}   ← 关联对象已自动展开
    images  图集       images    <#list item.imagesUrls as u>${u}</#list>  ← URL 已展开
  ═══════════════════════════════════════════════════════════
-->
<!DOCTYPE html>
<html>
<head>
  <title>${model.name} - ${web_name!''}</title>
</head>
<body>
<@fly_list_model model="products" rows="12" p="${p!1}">
  <ul>
  <#list dataList as item>
    <li>
      <a href="/products/${item.shortUrl}.html">${item.title}</a>
      <span>${(item.price)!''} 元</span>
      <#-- 关联字段：brandObj 由后端自动展开 -->
      <#if item.brandObj??><span>品牌：${item.brandObj.title}</span></#if>
      <#-- 图集字段：imagesUrls 为 URL 数组 -->
      <#if item.imagesUrls??>
        <#list item.imagesUrls as u><img src="${u}" /></#list>
      </#if>
    </li>
  </#list>
  </ul>
  <#if pageHtml??><div class="pager">${pageHtml}</div></#if>
</@fly_list_model>
</body>
</html>
```

**价值**：运营建完模型后，打开模板文件**直接看到**"我能用哪些标签 + 我有哪些字段 + 每个字段怎么写"。这消除了"后台能配、前台不会调"的断点，是让模型系统真正"零代码建站"的最后一环。

**实现要点**：
- `generateDefaultTemplates` 需要读取 `modelFieldDao.findFieldsByModelId(modelId, 1)`；
- 按 `FieldTypeEnum` 生成对应取值示例（`image` → `${item.xxxUrl}`、`images` → `<#list item.xxxUrls>`、`relate` → `${item.xxxObj.title}`、`select` → 原值直出）；
- 文件头注释由 `ModelFieldService` 提供的字段清单拼装。

#### 4.4.4 标签元数据接口（供前端"组件面板"用）

规划文档阶段 D 的"组件面板"需要标签清单数据。新增：

```
GET /api/system/tags/manual   （已存在，见 ApiTemplateController）
```

扩展其返回值，增加 `modelTags` 段落，输出通用模型标签的用法与参数说明（数据源可从 `AbstractModelTag` 的常量 + 注解提取，或直接内置 Java 常量）。**这样后台模板编辑器能"点击插入标签骨架"**，运营不需要背标签名。

### 4.5 标签使用决策树（写进文档，供后续参考）

```
模板里要放内容区块
  ├─ 这是一个"列表/瀑布流"        → <@fly_list_model model="xxx" rows="10">
  ├─ 列表要按分类筛选              → <@fly_category_model model="xxx"> 取分类 → 循环里嵌 list_model
  ├─ 要"最热/最多浏览"             → <@fly_hot_model model="xxx" rows="5">
  ├─ 详情页要"相关推荐"             → <@fly_rel_model model="xxx" category="${info.categoryId}" notid="${info.id}">

  ├─ 详情页要"动态渲染字段表"       → <@fly_fields_model model="xxx"> 遍历 fieldsList
  └─ 要"跨模型混排"（聚合栏目）      → 阶段 C 的 <@fly_list_channel channelIds="1,2,3">
```

### 5.3 表名生成链路（实测，改造范围就是这条链）

```
Web 层：ApiModelController.modelSave()
   └─ ModelService.addModel(model)
        ├─ model.setId(SnowFlake.getInstance().nextId())
        └─ modelTableService.createModelTable(model.getId(), null)   ← 传的是雪花 id
              └─ modelDataDao.createTable(SqlSafeUtil.safeNumber(modelId))
                    └─ XML: CREATE TABLE `fly_cmodel_${modelId}`      ← 拼表名

读取层：ApiModelController.dataList(@PathVariable Long modelId)
   └─ ModelDataService.selectPage(model.getId(), ...)
        └─ modelDataDao.selectPage(String.valueOf(modelId), ...)      ← 传的是 id 的字符串
              └─ XML: SELECT * FROM `fly_cmodel_${modelId}`

标签层：InfoModel / ListModel / PageModel / HotModel
   ├─ model = modelService.findModelByCode(modelCode)                ← 模板给的是 code
   └─ modelDataService.findDataById(model.getId(), id)               ← 又回到 id
```

**关键发现**：整个链路里，XML 参数名已经叫 `modelId` 但语义是"拼进表名的字符串"。改造的本质就是**把这个字符串的来源从「雪花 id」换成「code」**，并把白名单从 `safeNumber`（纯数字）换成 `safeTableSuffix`（标识符规则）。DAO 接口签名**不需要改**，只改传参值和校验方式。

## 6. 决策记录

以下为本次定案，写法沿用 `.agents/skills/flycms-dev/references/tech-debt.md` 的 ADR 风格。**实施后需把这 13 条追加进该文件。**

### D7. 模型物理表名 = `fly_cmodel_` + 模型 code（2026-09-24，用户定案）

- **方案**：物理表名 `fly_cmodel_{code}`，例如 `fly_cmodel_articles`。`code` 同时承担三种角色：前台路由目录名、后台模板目录名、物理表名后缀。
- **理由**：表名可读性是运维刚需——备份、排查慢查询、数据修复、跨环境迁移时，`fly_cmodel_articles` 一眼可知，`fly_cmodel_900000000000000003` 必须先查 `fly_model` 反查。三家对标 CMS（Dede/帝国/PHPCMS）均为这种"模型标识即表名"的形态。
- **代价（已知并接受）**：
  1. `code` 一经创建**永久锁定**，变更等于改表名 + 全量数据迁移（现有实现已锁定 `code`，本决策只是加重后果，需在创建表单显式警告）；
  2. `code` 的字符集必须严格白名单化（`^[a-z][a-z0-9_]{1,31}$`），否则表名会变成 SQL 注入面；
  3. 需一次性迁移已有 3 张表。
- **翻案条件**：出现"运营需要在创建后改 code"的真实诉求——届时唯一正解是提供「改 code = 自动 RENAME TABLE + 同步模板目录 + 写 301 跳转」的一键工具，而不是回退到 id 命名。

### D8. `fly_model` / `fly_model_field` 主键改自增，业务数据表保持雪花（2026-09-24，用户定案）

- **方案**：`fly_model.id`、`fly_model_field.id` 改 `bigint AUTO_INCREMENT`；`fly_cmodel_*` 的业务数据 `id`、`fly_article` 等存量业务表**一律不动**，继续 `SnowFlake.getInstance().nextId()`。
- **理由**：模型元数据是配置数据（单库、低频、行数量级 10~100），雪花的跨库唯一与高并发优势无用武之地，而 id 不可读的代价每天都在付（沟通时说"模型 900000000000000003"）。业务数据表是并发写入主体且未来可能分片，雪花是正确选择，且 2026-09-24 刚完成 SnowFlake 单例化修复（见 `docs/backend-bug-review-2026-09-24.md`），不应推翻。
- **边界**：本决策**只覆盖模型元数据两张表**，不是"全项目改自增"的信号。其他表是否改自增加，需单独立项评估。
- **翻案条件**：模型元数据需要跨库同步或多主写入——当前无此场景。

### D9. 存量 article 模块冻结并收敛为内置模型（2026-09-24）

- **方案**：`article` 独立模块**冻结新增需求**；`articles` 模型提升为唯一文章承载层；存量数据迁移后旧模块标记"经典版"过渡，最终下线。
- **理由**：见 §2.1 对照表。两套并行实现违反 DRY，且旧后台（FreeMarker HTML）与 vben 新后台并存会造成权限/功能双维护（技术债台账 #7）。
- **不做的事**：不删 `fly_article_comment`（评论功能不在模型系统覆盖范围，见 D11）；不引入多站点/多语言（沿用规划文档 §7.4 决策）。

### D10. 表名白名单独立化，禁止复用 `safeModelCode`（2026-09-24）

- **方案**：新增 `SqlSafeUtil.safeTableSuffix(String)` 专用于表名后缀校验，与 `safeModelCode`（路由/模板目录用）**分开**，即使当前规则相同。
- **理由**：两者安全边界不同——`safeModelCode` 出错的影响面是"路由 404 / 模板找不到"，`safeTableSuffix` 出错的影响面是"SQL 注入 + DROP TABLE"。安全边界不同的校验必须独立命名、独立演进、独立测试，不能因为当下规则巧合相同就合并。

### D11. 评论能力属平台层，不下放给自定义模型（2026-09-24）

- **方案**：自定义模型系统**不实现**评论子表/评论字段类型；评论统一走已有的 `fly_comment` 平台表（多态关联 `target_type` + `target_id`）。模型侧只保留"是否开启评论"开关与评论数冗余列 `count_comment`。
- **理由**：评论是横切能力（审核、敏感词、用户权限、通知、防刷），不属于任何单一内容模型。若每个模型自建评论表，则审核策略、反垃圾、统计逻辑要复制 N 份，且跨模型评论列表/后台审核无法统一。三家对标 CMS 也都把评论做成平台级组件。
- **落点**：模型详情的评论读取由标签（如 `fly_comment_list`）或独立接口承担，与模型表解耦；模型列表页的 `count_comment` 由评论服务回写（后续项）。
- **翻案条件**：出现"某模型需要与平台评论语义完全不同的独立评论"的真实诉求（如商品问答），届时建独立模型承载，而非给模型系统加评论表。

### D12. 七个模型标签收敛为单一通用标签族，禁止继续增生（2026-09-24）

- **方案**：`InfoModel`/`ListModel`/`PageModel`/`CategoryModel`/`RelModel`/`HotModel`/`FieldsModel` 收敛为**统一的模型标签族**，抽取公共基类 `AbstractModelTag`（参数解析、模型解析、分页装配、数据包装），各标签只保留差异化逻辑（排序、过滤、聚合方式）。同时**合并**语义高度重叠的 `ListModel` 与 `PageModel`（后者只是前者的分页变体，靠 `page`/`size` 参数区分）。
- **理由**：现状 §4.2 已量化——7 个标签里有 7 份几乎逐字复制的 `if ("model".equals(str))` 参数解析（每份约 30 行），改一处要改七处，且新增参数极易漏改。表名/主键改造同时动到这些标签的模型解析链路（`model.getId()` → `model.getCode()`），必须趁此收敛，否则改造面会翻七倍。
- **兼容性**：收敛**不破坏**模板兼容——保留全部现有标签名（`fly_info`/`fly_list`/`fly_page`/…）作为外观，仅内部实现继承 `AbstractModelTag`。新增标签走统一命名规范。
- **翻案条件**：出现某标签语义无法用族内参数表达的诉求——届时应扩展参数而非新增标签类。

### D13. 模型创建时自动生成"带注释的可用标签骨架"模板（2026-09-24）

- **方案**：`ModelService.generateDefaultTemplates(model)` 生成 `{code}/list.html`、`detail.html` 时，**不再写入静态骨架**，而是按该模型的**实际字段**生成：列表页逐字段生成 `<th>`/单元格，详情页逐字段生成标签行，并在模板顶部注入**本模型可用标签清单 + 参数说明 + 复制即用的示例注释块**（如 `<!-- 本模型可用标签：fly_list / fly_info / fly_fields ... 字段：title/author/... -->`）。
- **理由**：现状 §4.3 的最大缺失是"新建模型生成的模板是通用静态骨架，与新模型字段无关"，运营/AI 接手时要翻手册查标签用法。自动生成"字段感知 + 标签注释"的骨架，把"新建模块 → 打开模板 → 立即可用"闭合成环，是 §1 结论 5 的核心增量。
- **边界**：生成物是**骨架 + 注释**（占位符与示例），不是"成品页面"；字段变更时**不自动覆盖**已有模板（避免抹掉人工修改），仅在新建时生成，并提供"重新生成骨架"的手动按钮（带覆盖确认）。
- **翻案条件**：出现可视化拖拽编排模板的能力——届时骨架生成退化为"初始草稿"。

### D14. 补齐 6 类字段类型，其中 RELATE/RELATES 为 P1（2026-09-24）

- **方案**：在现有 15 种 `FieldTypeEnum` 基础上，补 6 类缺口字段类型——**P1 必做**：`relate`（单选引用其他模型记录）、`relates`（多选引用）；**P2 建议**：`tree_category`（树形分类选择，复用 `fly_category`）、`json`（结构化 JSON 字段）；**P3 可选**：`formula`（计算列，如 `price * qty`）、`version`（版本/修订号）。
- **理由**：现状 §3.3 逐项核验——现有类型覆盖 90% 内容建模场景，但"关联引用"是内容建模的刚需（文章→作者、商品→品牌、问题→答案），缺失会导致用户用 `input` 手动填 id，既易错又无法在后台做友好选择器。树形分类是栏目/多级分类场景刚需。故 P1 两项必须随本次改造落地。
- **实现代价**：RELATE/RELATES 需在 `fly_model_field` 增列 `relate_model`（被引用模型的 code），并配套前台选择器组件与动态表单渲染分支；存储层存被引用记录的 `id`（多个用逗号分隔，与现有 images/files 一致）。
- **翻案条件**：无——这是能力补齐，只可能追加更高级类型（如富关联、反向关联查询）。

## 7. 改造一：表名标识与命名校验

### 7.1 命名规则（最终定案）

| 项 | 规则 | 说明 |
|---|---|---|
| 正则 | `^[a-z][a-z0-9_]{1,31}$` | 小写字母开头，总长 2~32 |
| 首字符 | 必须为 `[a-z]` | 禁止数字开头（避免 `fly_cmodel_1` 与旧 id 表名混淆） |
| 允许字符 | `a-z`、`0-9`、`_` | **不允许**中文、大写、连字符、空格 |
| 保留字 | 见 §15.2 黑名单 | 含 SQL 保留字 + MySQL 关键字 + 项目已有表后缀 |
| 唯一性 | `fly_model.code` 全局唯一（数据库 `uk_code` + 应用层预检） | 同时天然保证表名唯一 |
| 长度上限 32 | 表名总长 = `len("fly_cmodel_")=11` + 32 = 43 < MySQL 64 上限 | 留足余量 |

> **关于"支持中文表名"**：用户在方案选择中提出过该诉求，但最终定案为**表名只用 ASCII code**。中文表名会让 `SqlSafeUtil` 的白名单退回黑名单模式（必须枚举所有危险字符），SQL 注入防线失守风险远大于可读性收益。中文友好名由 `fly_model.name`（如"文章模型"）承担——它就是给人看的，`code` 只管机器。**如需中文路由，用栏目体系的 `fly_channel.channel_name`，不要动 code。**

### 7.2 `SqlSafeUtil` 改造

```java
// core/utils/SqlSafeUtil.java 新增（D10：独立于 safeModelCode，安全边界不同）

/**
 * 模型物理表名后缀白名单（= fly_model.code）。
 * 与 safeModelCode 规则相同但必须独立：本方法的出错影响面是 SQL 注入/误删表，
 * safeModelCode 的出错影响面仅为路由 404，二者安全等级不同，禁止合并。
 */
private static final Pattern SAFE_TABLE_SUFFIX = Pattern.compile("^[a-z][a-z0-9_]{1,31}$");

/** 表名后缀黑名单：SQL 保留字 + 项目已有表名片段，防与既有表撞名 */
private static final Set<String> RESERVED_TABLE_SUFFIX = Set.of(
        // —— SQL 保留字（拼进表名后仍是标识符，防语义歧义）——
        "order", "group", "select", "insert", "update", "delete", "where", "index", "key",
        "table", "values", "limit", "union", "having", "distinct", "column", "database",
        "schema", "create", "drop", "alter", "join", "left", "right", "desc", "asc",
        // —— 与既有 fly_ 系表撞名（表名 = fly_cmodel_ + suffix，故校验前缀冲突）——
        "admin", "admin_log", "article", "article_category", "article_comment", "images",
        "model", "model_field", "model_category", "user", "config", "channel", "block",
        "template", "form", "guide", "links", "job", "score", "message");

public static String safeTableSuffix(String code) {
    if (code == null || !SAFE_TABLE_SUFFIX.matcher(code).matches()
            || RESERVED_TABLE_SUFFIX.contains(code)) {
        throw new IllegalArgumentException("非法模型标识（表名后缀）：" + code);
    }
    return code;
}
```

> **为什么 `images` 在黑名单里？** 因为 `fly_cmodel_images` 虽不与 `fly_images` 直接撞名，但人为排查时极易混淆。同理 `model`、`article` 等。这条黑名单是"防混淆"而非"防冲突"，成本极低、收益是长期的认知清晰。

### 7.3 `ModelDataDao.xml` 改造

把 6 处 DDL/DML 里的 `${modelId}` 语义改为"表名后缀"（**变量名保留 `modelId` 以减少 diff 面，但注释必须更新**）：

```xml
<!-- ${modelId} 语义 = fly_model.code（安全边界：SqlSafeUtil.safeTableSuffix 白名单，见 D7/D10） -->

    CREATE TABLE IF NOT EXISTS `fly_cmodel_${modelId}` (
      ...
    ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
</update>
```

    WHERE table_schema = DATABASE() AND table_name = CONCAT('fly_cmodel_', #{modelId})

## 8. 改造二：主键策略（自增 vs 雪花）

### 8.1 结论

| 表 | 现状 | 改为 | 理由 |
|---|---|---|---|
| `fly_model.id` | `bigint(20) unsigned NOT NULL`（雪花） | `bigint(20) NOT NULL AUTO_INCREMENT` | 配置数据，单库低频，需人眼可读 |
| `fly_model_field.id` | `bigint(20) unsigned NOT NULL`（雪花） | `bigint(20) NOT NULL AUTO_INCREMENT` | 同上 |
| `fly_model_category.id` | 已是 `AUTO_INCREMENT` | **不动** | 现状已是最优 |
| `fly_cmodel_*.id`（业务数据） | 雪花 | **不动** | 并发写入主体，未来可能分片 |
| `fly_article` 等存量业务表 | 雪花 | **不动** | 同上，且已修复 SnowFlake 单例化 |

### 8.2 关键副作用：内置模型的硬编码 ID 必须废弃

现状代码与 SQL 中大量硬编码 `900000000000000003` 这类雪花 id（`sql/model-modules.sql` 里的字段 insert、`fly_cmodel_*` 建表语句、种子数据）。**改自增后这些硬编码 id 全部失效**，必须改为按 `code` 查询：

```java
// ❌ 改造前：硬编码雪花 id（自增后必然错位）
Long modelId = 900000000000000003L;

// ✅ 改造后：按 code 查（code 是稳定业务标识）
Model model = modelService.findModelByCode("articles");
if (model == null) { return DataVo.failure("模型不存在"); }
Long modelId = model.getId();
```

**受影响文件清单**（需逐一排查硬编码）：

- `sql/custom-model.sql`：种子模型的 `fly_model` insert + `fly_cmodel_*` 建表语句
- `sql/model-modules.sql`：`articles` 模型的字段 insert + `fly_cmodel_900000000000000003` 建表 + ALTER
- `sql/stage-*.sql`：检查是否有模型 id 引用
- Java 侧：全文搜索 `9000000000000` 字面量（预计 0 处业务代码，主要是 SQL 与文档）

> **重要**：`fly_cmodel_*` 表的 `id`（业务数据主键）**仍是雪花**，所以 `sql` 里那些表的 `PRIMARY KEY (id, short_url)` 结构不变，只改**表名**（§7）。这两件事不要混。

### 8.3 `Model` / `ModelField` 实体与 DAO 改动

**实体**：`id` 字段类型不变（`Long`），无需改 Java。但 insert 语句要调整——自增列不能显式传值（或传 `null`）。

```xml
<!-- ModelDao.xml：addModel 去掉 id 列，交由 AUTO_INCREMENT -->
<insert id="addModel" useGeneratedKeys="true" keyProperty="id">
    insert into fly_model (name, code, title_label, is_system, list_template, detail_template,
                           icon, description, sort, status, create_time)
    values (#{name}, #{code}, #{titleLabel}, #{isSystem}, #{listTemplate}, #{detailTemplate},
            #{icon}, #{description}, #{sort}, #{status}, now())
</insert>
```

> `useGeneratedKeys="true" keyProperty="id"` 让 MyBatis 回填自增主键到实体——`ModelService.addModel` 后续要用 `model.getId()` 建表，这个回填是**必需**的，否则拿到 null。

**Service 改动**：

```java
// ModelService.addModel()：删掉 setId(雪花)，改为依赖自增回填
- model.setId(SnowFlake.getInstance().nextId());
  model.setIsSystem(0);
  ...
  if (modelDao.addModel(model) <= 0) {           // 回填后 model.getId() 可用
      return DataVo.failure("保存失败");
  }
- modelTableService.createModelTable(model.getId(), null);
+ modelTableService.createModelTable(model.getCode(), null);   // 传 code 而非 id
```

`ModelFieldService` 同理。

### 8.4 为什么不全项目改自增

**明确记录，避免后续反复讨论**：雪花 ID 在本项目业务表上是**正确选择**——

1. 模型数据表并发写入量大，自增在 InnoDB 下有 `AUTO-INC` 锁竞争（`innodb_autoinc_lock_mode` 虽已是 2 但仍非零成本）；
2. `short_url` + `id` 联合主键的设计依赖 id 的全局唯一性来避免跨表冲突；
3. 未来若做分表/分库，自增 ID 必须改造，雪花天然支持；
4. 2026-09-24 刚修复的 SnowFlake 单例化问题证明这条路已经走通，推翻等于浪费。

**判断标准**：数据是"给机器用的（海量、并发、需分片）"→ 雪花；数据是"给人看的（少量、低频、需沟通）"→ 自增。模型元数据属于后者。

## 9. 改造三：存量数据迁移

### 9.1 迁移总览

| 原表名 | 新表名 | 动作 |
|---|---|---|
| `fly_cmodel_900000000000000001` | `fly_cmodel_images` | `RENAME TABLE` |
| `fly_cmodel_900000000000000002` | `fly_cmodel_downloads` | `RENAME TABLE` |

### 9.2 迁移 SQL（新增 `sql/model-naming-migration.sql`）

```sql
-- ============================================================
-- 模型表名改造迁移：fly_cmodel_{雪花id} → fly_cmodel_{code}
-- 依据：《内容体系收敛与模型命名改造开发方案.md》§6/§7（ADR D7）
-- 前置：备份数据库（见 §9.3）
-- 执行：mysql -u<user> -p --default-character-set=utf8mb4 flycms < model-naming-migration.sql
-- 号段：本脚本不新增权限行（无新菜单），仅数据/结构迁移
-- ============================================================

-- ---------- 步骤 1：删除测试模型（无数据价值） ----------
DROP TABLE IF EXISTS `fly_cmodel_1299270553286488064`;
DELETE FROM `fly_model_field` WHERE `model_id` = 1299270553286488064;
DELETE FROM `fly_model` WHERE `code` = 'testdemo';

-- ---------- 步骤 2：物理表重命名（RENAME 是元数据操作，秒级完成，不搬数据） ----------
RENAME TABLE `fly_cmodel_900000000000000001` TO `fly_cmodel_images`;
RENAME TABLE `fly_cmodel_900000000000000002` TO `fly_cmodel_downloads`;
RENAME TABLE `fly_cmodel_900000000000000003` TO `fly_cmodel_articles`;

-- ---------- 步骤 3：主键改自增 ----------
-- 前置确认（必须先跑，看清索引结构再改）：
--   SHOW CREATE TABLE `fly_model`;
--   SHOW CREATE TABLE `fly_model_field`;
-- 结构现状（实测）：
--   fly_model       PRIMARY KEY (id)，id 无 AUTO_INCREMENT，另有 UNIQUE KEY uk_code(code)
--   fly_model_field PRIMARY KEY (id)，id 无 AUTO_INCREMENT，另有 UNIQUE KEY uk_model_field(model_id, field_name)
-- 说明：MySQL 要求 AUTO_INCREMENT 列必须是某个键的首列。两表 id 均已是主键首列，
--       因此只需在同一条 ALTER 里 MODIFY（加 AUTO_INCREMENT）+ DROP/ADD PRIMARY KEY。

-- 3.1 fly_model
ALTER TABLE `fly_model`
  MODIFY COLUMN `id` bigint(20) NOT NULL AUTO_INCREMENT COMMENT '模型ID（自增，原雪花）',
  DROP PRIMARY KEY,
  ADD PRIMARY KEY (`id`);

-- 3.2 fly_model_field
ALTER TABLE `fly_model_field`
  MODIFY COLUMN `id` bigint(20) NOT NULL AUTO_INCREMENT COMMENT '字段ID（自增，原雪花）',
  DROP PRIMARY KEY,
  ADD PRIMARY KEY (`id`);
-- 注意：uk_model_field(model_id, field_name) 是独立 UNIQUE KEY，DROP PRIMARY KEY 不影响它，无需重建。

-- 3.3 校验自增生效
SHOW CREATE TABLE `fly_model`;        -- 期望：id ... NOT NULL AUTO_INCREMENT
SHOW CREATE TABLE `fly_model_field`;  -- 期望：同上

-- ---------- 步骤 4：重排现有数据的自增起始值（可选，让内置模型 id 变友好） ----------
-- 现状：images=900000000000000001 / downloads=...002 / articles=...003
-- 若希望内置模型 id 变为 1/2/3，按 code 顺序重建（注意：会改变 id，需同步 field.model_id）
-- ⚠️ 这一步是可选的。若跳过，自增从 900000000000000004 起步，不影响功能。
-- 推荐做法：保留原 id 不动（自增只是"未来新模型"的生成方式），零风险。

-- ---------- 步骤 5：校验 ----------
SELECT '模型数' AS item, COUNT(*) AS cnt FROM fly_model
UNION ALL SELECT '字段数', COUNT(*) FROM fly_model_field
UNION ALL SELECT 'cmodel 表数', COUNT(*) FROM information_schema.tables
  WHERE table_schema = DATABASE() AND table_name LIKE 'fly_cmodel\_%';
```

> **关于步骤 3 的 `DROP PRIMARY KEY`**：MySQL 要求在一条 `ALTER` 内完成 `MODIFY ... AUTO_INCREMENT` 与主键重建（若分成两条，中间态会因"自增列不属于任何键"而报 `ERROR 1075`）。两表 id 均已是主键首列，故上述写法可行。**执行前必须先 `SHOW CREATE TABLE` 确认**；若你的库中 id 上另有唯一索引，可先 `DROP` 该唯一索引再执行，避免"重复索引"警告。

### 9.3 备份要求（强制）

```bash
# 迁移前必须执行，且确认文件非空
mysqldump -u<user> -p --default-character-set=utf8mb4 flycms \
  fly_model fly_model_field fly_model_category \
  fly_cmodel_900000000000000001 fly_cmodel_900000000000000002 fly_cmodel_900000000000000003 \
  > backup-before-model-rename-$(date +%Y%m%d%H%M).sql
```

**回滚方案**：`RENAME TABLE` 可逆，直接反向着改回；主键改自增不可逆（自增值丢失），但**流程上无数据损失**（只影响新插入的 id 形态）。因此：
- 表重命名阶段可即时回滚；
- 主键改自增阶段建议在停机窗口执行，完成即验证。

### 9.4 应用层同步点

迁移 SQL 执行后，**代码必须先改完再重启**，否则会以旧规则拼表名导致"表不存在"：

1. `ModelTableService.createModelTable(code, fields)` — 传参改 code
2. `ModelDataService` 全部 `String.valueOf(modelId)` → `model.getCode()`（共 11 处，见 §8）
3. `ModelService.addModel` — 删 setId、传 code（见 §2.3/§8.3）
4. `SqlSafeUtil.safeNumber` 在模型表名场景全部替换为 `safeTableSuffix`

**顺序建议**：停机 → 备份 → 跑迁移 SQL → 发新代码 → 启动 → 冒烟。中途不启动旧代码。

### 10.3 附件语义冲突（通用坑，必读）

**这是收敛过程中最容易踩的坑**：旧模块的图片字段**存 URL 字符串**，而模型系统的 `image`/`images` 字段**存 `fly_images.id`**（配合引用计数）。

实测证据：

| 表 | 图片列 | 存储形态 |
|---|---|---|
| `fly_topic` | `topic_image` varchar(255) | **URL 字符串** |
| `fly_images` | `img_url` varchar(255) | URL（主键 id 是雪花） |
| `fly_cmodel_*` | `thumbnail` bigint | **`fly_images.id`** |

而 `fly_images` 实测 **0 行**——意味着"把旧 URL 反查成 id"这条路**必然失败**（库里没有对应记录）。

**处理方案（推荐）**：给收敛后的模型**加一个 `input` 类型字段**存原始 URL（如 `topic_image_url`），**不做 id 转换**。理由：

1. 数据只有 18 行，人工核对成本低；
2. 强行补 `fly_images` 记录会引入"孤儿图片 + 引用计数为 0"的脏数据；
3. 模型系统同时支持两种图（`image` 走 id、`input` 走 URL），模板层统一渲染即可。

**长期方案**：规划文档阶段 B 的"附件库"上线后，在后台提供一个"URL 批量导入 `fly_images`"工具，让存量 URL 转为标准引用。**但这不该由本次收敛承担。**

### 10.4 URL 迁移（Nginx 301）

```nginx
# 存量内容 URL 301 到模型 URL（渐进迁移，不毁 SEO）
# ---- 文章 ----
location ~ ^/article/([0-9]+)\.html$ { return 301 /articles/$1.html; }
location ~ ^/a/([a-zA-Z0-9]+)\.html$  { return 301 /articles/$1.html; }
location ~ ^/article/(.*)$             { return 301 /articles/$1; }
# ---- 分享 ----
location ~ ^/share/(.*)$    { return 301 /shares/$1; }
# ---- 问答 ----
location ~ ^/question/(.*)$ { return 301 /questions/$1; }
# ---- 话题 ----
location ~ ^/topic/(.*)$    { return 301 /topics/$1; }
```

> **纪律**：
> 1. 用 **301**（永久重定向，传递 SEO 权重），不用 302；
> 2. **部署 Nginx 前旧路由必须还在线**（先切前台 → 再加 301 → 观察 → 撤旧路由）；
> 3. 新 `code` 不得与既有前台路由前缀冲突——`articles`/`shares`/`questions`/`topics` 均为复数，与单数旧前缀不冲突（这条已在规划文档阶段 C 的 URL 唯一性校验清单覆盖）。

### 10.5 收敛完成判定标准

一个模块算"收敛完成"，需同时满足：

1. **前台**：新 URL（`/{code}/**`）可访问，旧 URL 301 到新 URL，页面内容与旧版一致；
2. **后台**：在 vben 的模型内容管理页可完成增删改查审核，无需打开旧后台；
3. **代码**：旧控制器（`web/system/XxxAdminController`）、旧前台控制器、旧标签类**已删除或标记 `@Deprecated`**；
4. **模板**：旧模板目录（`pc_theme/{skin}/{old}/`）已合并/删除；
5. **数据**：旧表保留但**无代码引用**（用 IDE 全局搜索表名验证返回 0 处）；
6. **观察期**：连续 2 周无线上问题。

### 15.4 风险清单

| # | 风险 | 等级 | 应对 |
|---|---|---|---|
| 1 | 迁移期间应用未同步重启 → 表不存在 | **高** | 停机窗口执行；先跑 SQL 再发代码再启动，中途不启旧代码 |
| 2 | `fly_model` / `fly_model_field` 主键改自增的 `ALTER` 报 `ERROR 1075` | 中 | 必须把 `MODIFY AUTO_INCREMENT` 与 `DROP/ADD PRIMARY KEY` 写在**同一条 ALTER** 里（§9.2 步骤 3）；执行前 `SHOW CREATE TABLE` 确认索引结构 |
| 3 | 硬编码雪花 id 遗漏 → 迁移后取不到模型 | 中 | 全文搜 `9000000000000` 字面量；单测覆盖 `findModelByCode` |
| 4 | 文章分类 ID 冲突未处理 → 迁移后文章归错分类 | **高** | 强制使用映射表（§10.2 坑 1），迁移后抽样校验分类归属 |
| 5 | `code` 与前台既有路由前缀冲突 | 中 | 复用规划文档 §8 阶段 C 的 URL 唯一性校验清单（model code + front 固定前缀 + channel dir 三方比对） |
| 6 | 运营在创建后要求改 `code` | 中 | 明确拒绝（D7），表单显式警告；若诉求强烈，单独立项做"改 code 一键工具" |
| 7 | Nginx 301 配置与旧路由未同时在线 → 期间 404 | 中 | 部署顺序：先保留旧路由 → 加 301 → 观察 → 撤旧路由 |
| 8 | 标签收敛破坏既有模板（改 `AbstractModelTag` 时漏改某标签） | **高** | 保留全部旧标签名与参数语义；上线前对每个标签写一个回归用例（§13 标签类别 4 条） |
| 9 | 自动生成骨架覆盖了人工修改的模板 | **高** | 仅在**新建时**生成；手动"重新生成"必须带覆盖确认（D13）；Service 层禁止在 `updateModel` 里调生成 |
| 10 | `relate` 字段的被引用记录被删除 → 悬空引用 | 中 | 展示层做"已删除"降级文案；删除被引用模型时给出警告（不强制级联，避免误删） |
| 11 | `relates` 多值存储逗号分隔 → 无法走索引精确匹配 | 低 | 接受（与现有 images/files 一致）；若将来需要反向查询，再评估关联中间表 |
| 12 | `topic` 字段映射遗漏（如 `topic`→`title`） | 中 | 迁移前按 §10.2 映射表逐字段核对；迁移后抽 5 行人工比对 |
